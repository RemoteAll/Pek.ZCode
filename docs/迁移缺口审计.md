## 四、核对中发现台账写错（重要）

`docs/移植对照-NCode.md` 原先记着 **「`MSPageSplit`（SQL Server 2000/2005 的 TOP + NOT IN / 双 TOP / ROW_NUMBER 分页）未移植」**。
本轮核对发现 `src/pagesplit.zig` **早已实现全部四条算法**：

- `pageSplitAlloc`（分支判定，对应 `MSPageSplit.PageSplit`）
- `topNotInAlloc` / `doubleTopAlloc` / `maxMinAlloc` / `rowNumberAlloc`
- 另有一个 `Builder`（C# `SelectBuilder` 的最小子集）与 `reverseOrderBy`

**结论：这条台账是错的，已在下游文档里改正**。教训与 `docs/移植对照-NCode.md` 末尾那句一致——
「不确定性要 grep 代码，不要凭上一轮的记录」；这次是反方向的错误（把已做的记成没做），同样会误导排期。

> 附带说明：本轮我先按台账写了一份 `mspage.zig` 重复实现，核对到 `pagesplit.zig` 后**立即删除**，
> 没有留下两份分页算法。

## 五、判定为「不适用」的项（附理由）

判定标准：**C# 侧存在的目的就是为了绕开 .NET 的语言/框架限制**，而 Zig 侧根本不共享那个限制。
这些不算缺口，但必须写清楚，否则下次又会有人去找「为什么没有 KeyedLocker」。

| C# 类型 | 它解决什么 | 为什么 Zig 不需要 |
|---|---|---|
| `Common/KeyedLocker<T>` | **internal** 工具：8 个共享锁对象 + `hash(key) % 8`，给「同一个表名串行化」用 | Zig 侧没有「全局可变工厂 + 静态锁表」这种结构：表名/连接是**参数**，并发由调用方持有的 `Mutex`/连接池控制；`cache.zig`/`dbcache.zig`/`entity_queue.zig` 各自持有自己的锁 |
| `Entity/EntitySplit.Split(factory, conn, table, func)` | 临时把工厂指向某张物理表/某连接，`using` 结束还原 | 本仓的 `dbtable` / `shards` 一律显式传（连接名 + 物理表名），**没有需要「切了再还原」的全局状态** |
| `Entity/DataRowEntityAccessor` | .NET `DataRow` ↔ 实体互转 | 本仓没有 `DataSet`/`DataRow`；等价能力是 `entity.fromRow` / `entity_ext`（Row → 实体）与 `dbtable_packet`（二进制行列包） |
| `Common/ValidHelper` | `ToInt32/ToDecimal/ToDateTime...` 的安全转换 | 等价能力在 `zzig.db.Value`（`asI64/asF64/asText/...`）与 `types.zig`，且**失败返回 null 而不是静默给默认值**（更严格） |
| `Linq/`（IQueryable + 表达式树） | 让 C# 能用 lambda 写查询，翻译成 SQL | Zig 没有表达式树/运算符重载，等价表达是 `query.Where/Query` + `sqlbuild`（选列/条件/排序/分页/聚合都能表达）；**这是形态差异，不是能力缺失** |
| `Configuration/DbConfigProvider` | 把 Model.xml/连接串塞进 .NET 的 `IConfiguration` | Zig 无 `IConfiguration`；对应能力是 `setting.zig`（全局配置）+ `parseConnectionString` |
| `Services/DbController`、`LoginInfo` | ASP.NET MVC 控制器与登录上下文 | HTTP 侧能力由 `dbservice.zig` 的端点 + `dbclient.zig` 覆盖；MVC 绑定/登录态属于 Web 框架，不在 ORM 范围 |

## 六、核对方法（可复现）

```powershell
# 1) C# 侧目录与文件清单
Get-ChildItem 'G:\Code\Pek.FrameWork\DH.NCode\DH.NCode' -Directory |
```
