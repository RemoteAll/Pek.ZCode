## 三之二、性能视角核对（亿级设备 / 多系统共用表 / 分库分表）

用户口径：**「这个 ORM 库就是要考虑支持至少上百万甚至上亿物联网设备高并发以及多系统共用数据库表、
分库分表等应用场景的」**。所以迁移之外，单独按「大规模下会不会炸」核了一遍：

| 能力 | 本仓实现 | 证据 | 结论 |
|---|---|---|---|
| 批量写（多行 INSERT / UPSERT / LOCAL INFILE） | `dbtable.insertBatch` / `upsertBatch` / `loadDataBatch` | `dialect.maxStatementParams`：SQLite 32766 / MySQL 65535 / **SQL Server 2100** / Oracle 65535 | ✅ 按方言自动分批 |
| 连接池 | `pool.zig` | `Options{ max_size=16, idle_timeout_ms=300s, prewarm }` + 借出/归还统计 | ✅ |
| 分库分表 | `shards.zig` + `Dal.tableShard` / `tableShardOn` | 跨库分片、分片表自动建表、批量写按「连接+物理表」分组 | ✅ |
| 多系统共用表 | `dbcache.CacheInvalidator` | 分布式版本号 + `checkRemote()` 默认 1s 轮询比对（热路径不碰网络） | ✅ |
| 缓存占用上限 | `cache.zig` | `MaxCacheCount` 硬上限、装载带 `LIMIT max_rows+1`、超限**一行不留** + 60s 静默期 | ✅ |
| 大表行数 | `Dal.countUpTo` / `countTotal` | `LIMIT n+1` 恒定成本；大表走统计估算，无统计时警告后退回精确 | ✅ |
| 统计字段并发写 | `dbtable.accumulate` | SQL 侧 `col = col + ?` 原子累加，避免读-改-写丢更新 | ✅ |
| **大表遍历（本轮修复）** | `extract.{Id,Paging,Time}Extractor.next()` | **本轮新增：每次 `next()` 开头回收上一页**（`Session.resetResults`）；用例实测 400 行 / 20 页峰值 arena **< 16KB** | ✅ 修好了（原来无界） |
| 语句复用 | SQLite 语句缓存 / MySQL 预处理句柄 / PG 命名预处理 | 同进程 A/B：MySQL 点查 1.64×、插入 1.6×；PG 1.64× / 1.5~1.6× | ✅（ODBC / Oracle 无缓存，已写清） |
| 只取需要的列 | `Query.column` | — | ✅ |
| 延迟写队列 | `entity_queue`（满额/到期 flush、带事务） | — | ✅ |
| **高并发正确性（本轮新增）** | `tests/integration_concurrency.zig` | 4 线程 × 100 次，**各自独立连接 + 同一个 WAL 库文件**：并发插入 → 400 行不丢不重（Id/Code 各自 400 个不同值）；并发累加同一行 `Total+1` → 恰好 400（不丢更新）；`getOrAdd` 4 线程 × 25 次同键 → **只插 1 行、created 仅 1 次**；连接池 8 线程 × 40 次共享借还（上限 4）→ 新建 4 / 复用 320（98.8%）/ 无泄漏 | ✅ 有回归用例 |

**本轮发现并修复的真问题**：三个分页抽取器此前**从不回收**会话结果 arena——单页 5000 行没问题，
但按页遍历一张千万级表时，20 页就攒下全部行，内存随页数线性上升（在亿级场景下必然 OOM）。
修复后内存有界，并加了实测用例守住（`max_arena < 16KB`）。

**明确边界（不假装支持）**：
- `dbtable.queryRows` / `Session.queryRows` 是**全量**语义（结果全进 arena）；大表请用 `extract.*`；
- `Session` 的结果内存由调用方管：手工分页循环时要自己周期性 `s.resetResults()`；
- ODBC / Oracle 驱动没有语句缓存（每次 prepare），已在各自文件头写清；
- `queryRows` 没有「行数上限」保护，`Query.take/page` 要调用方自己给（加硬上限会破坏既有语义）。
  → **2026-11-14 已补护栏**：`Setting.MaxQueryRowsWarn`（默认 10 万，只告警）/ `Setting.MaxQueryRows`（默认 0 = 不限，超限报 `error.TooManyRows`），
  在 `TableRef.queryRows` 与 `Session.queryRows` 两个全量入口生效——默认行为不变（不误伤存量调用方），要拦就配上硬上限。

**顺带踩到的坑（已写进代码注释）**：`Dal.initWithModel` **接管模型所有权**（`Dal.deinit` 里会
`model.deinit()`），调用方再 `m.deinit()` 就是双重释放——本轮写用例时直接段错误。

## 四、核对中发现台账写错（重要）

`docs/移植对照-NCode.md` 原先记着 **「`MSPageSplit`（SQL Server 2000/2005 的 TOP + NOT IN / 双 TOP / ROW_NUMBER 分页）未移植」**。

- 另有一个 `Builder`（C# `SelectBuilder` 的最小子集）与 `reverseOrderBy`

**结论：这条台账是错的，已在下游文档里改正**。教训与 `docs/移植对照-NCode.md` 末尾那句一致——
「不确定性要 grep 代码，不要凭上一轮的记录」；这次是反方向的错误（把已做的记成没做），同样会误导排期。

## 五、逐项复核「不适用」（2026-11-14 二次核对，用户质疑后重做）

> 用户原话：**「## 判定「不适用」的 7 项（附理由，避免下次又去找） 这里是真不适用吗？」**
>
> 这个质疑是对的：第一版我按「C# 那份代码长什么样」判，没问「它**支撑的能力**本仓有没有」。
> 复核方法改成两步：① 先查 C# 类型**被谁调用**（能力在哪个业务上）；② 再查本仓有没有那个业务能力。
> 结果 **2 项其实是真缺口，已补齐**；5 项确实不适用（理由换成"能力在哪覆盖"而不是"Zig 没这语法"）。

### 5.1 真缺口（已补，不是不适用）

| C# 类型 | 它支撑的业务能力 | 本仓缺口 | 落地 |
|---|---|---|---|
| `Common/KeyedLocker<T>` | **`Entity<T>.GetOrAdd(key)`**：get-or-create 时按 key 串行，防并发重复插入（调用点 `Entity.cs:2277 / 2326`，加锁后**二次查库**再插） | ❌ 本仓**没有 `getOrAdd`**，也就没有这把锁 | ✅ `src/keyed_lock.zig`（8 条带条带锁，与 C# 同粒度）+ `entity.getOrAdd`（无锁查 → 按主键值加锁 → **二次查** → 事务内插入） |
| `Entity/DataRowEntityAccessor` | **`LoadData<T>(DataTable/DbTable/IDataReader)`**：把任意表格数据批量转实体列表 | ❌ 只有单行 `fromRow`，没有批量入口 | ✅ `entity.fromRows`（批量 + 字符串/二进制**深拷贝**，避免借用结果集缓冲） |

说明：`getOrAdd` 的锁 key 是**业务主键值**拼接（`Value` 的文本形式，NULL 用 `∅` 占位）。
自增主键表用不上它——新行主键由库生成，锁 key 无从预先给出；C# 侧也是拿业务键调的。

### 5.2 确认不适用（理由已换成「能力在哪覆盖」）

| C# 类型 | 能力 | 本仓覆盖在哪 |
|---|---|---|
| `Entity/EntitySplit.Split(factory, conn, table, func)` | 临时把工厂指向某张物理表/某连接 | `Dal.tableShard` / `Dal.tableShardOn`（按分片值算出物理表）+ `dbtable` 的 API 直接接收 `TableRef`；**本仓没有需要"切了再还原"的全局状态**，所以不需要这层包装 |
| `Common/ValidHelper`（`ToInt32/ToDecimal/ToDateTime/ToEnum/ToObject<T>` + `ToXxxArray`） | 任意值 → 目标类型的安全转换（失败给默认值） | 标量：`zzig.db.Value.asI64/asF64/asText/asBool...`（且**失败返回 null 而非静默默认值**，更严格）；数组：调用方按需 `for (values)` 逐个转——C# 的 `ToXxxArray` 只是 `ToArray(value, ToXxx)` 的薄封装，**没有额外语义** |
| `Linq/`（`EntityQueryable`/`EntityQueryProvider`/`LinqExtensions`） | 用 lambda 写查询并翻译成 SQL | `query.Where` 已有 15 个算子：`eq/ne/gt/ge/lt/le/like/notLike/in/notIn/between/isNull/notNull/raw/anyLike` + `Query.column/filter/orderBy/page/take/skip`。C# 的表达式树是**语法层**的便利，不是多出来的查询能力 |
