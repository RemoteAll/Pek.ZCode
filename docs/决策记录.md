## 2026-11-11 表归属连接的判定：`tableConn / tableBelongsToConn / tablesOfConn`

- **用户原话**：「C#的是不是ORM组件本身就会一起解析的，如果是的话，当前Rust和Zig版本的是不是也要有，而且更方便带出？」「需要的」
- **背景**：C# `DH.NCode` 解析 `Model.xml` 时就把 `TableItem.ConnName`（缺省用 `EntityModel.ConnName`）
  与 `Field.Description` 挂在实体上。Zig 侧 `model.zig` 本来已经按实体名/物理表名、属性名/`ColumnName` 反查，
  唯独**「这张表属于哪条连接」**要消费方自己写（表级优先、否则模型级）。
- **本轮新增**（与 Rust `Pek.RCode` 同名 API 语义逐条对齐）：
  - `EntityModel.modelConn()`：模型级连接名（缺省/空白 → null）；
  - `EntityModel.tableConn(meta)`：表**实际归属**的连接（表级优先，否则模型级；两级都没配 → null = 由调用方默认连接代管）；
  - `EntityModel.tableBelongsToConn(meta, conn)`：是否归属指定连接（忽略大小写；两级都没配视为归属）；
  - `EntityModel.tablesOfConn(gpa, conn)`：按连接取表（返回 `[]*const TableMeta`，调用方负责 `free`）。
- **注意**：参数名用 `meta` 而不是 `table` —— Zig 0.17 里参数名与方法名 `table` 冲突（`function parameter shadows declaration`）。
  `test` 块上也不能挂 `///` 文档注释（`documentation comments cannot be attached to tests`），用普通 `//`。
- **验证**：新增 `test "表归属连接：表级优先，否则模型级"`（表级优先 / 忽略大小写 / 按连接取表 / 两级都没配归调用方）；
  `zig build test --summary all` → **5/5 steps succeeded，test success**（unit + integration 全绿）。
- **配套**：Rust `Pek.RCode` 已提交 `9af228f`（`feat(model): 公开「表归属哪条连接」的判定`）。

## 2026-11-11（三）MySQL 绿色执行驱动 + 单对象缓存 + 生产模型回归

- **用户原话**：
  - 「**MySQL 执行驱动** 不是说了参考Rust有一个绿色版本么？」（前一轮我把 MySQL 列为「必须先要连接串」的候选，用户指出 Rust 侧本来就是**纯协议绿色实现**，不需要本地库也能做）。
  - 「把 `zzig` 的 2 个本地提交 这个已经提交了」（zzig 两个提交已推送完毕，本轮从 `origin/main` 起算）。
- **结论**：MySQL 走**纯 wire protocol**（不加载 `libmysqlclient`），落在公共库 `zzig.db.mysql`，本仓只做方言/会话接线。

### 1. 新增 `zzig.db.mysql`（绿色驱动）

- **为什么在 zzig**：与 `zzig.db.sqlite` 同级，任何项目都能复用；本仓不复制实现。
- **协议覆盖**：
  - 握手 v10 解析（capability 高低位、scramble 分两段、插件名）；
  - `mysql_native_password`（完整）+ `caching_sha2_password`（**仅 fast auth**）；
  - `COM_QUERY` 文本协议（DDL / 无参查询）；
  - `COM_STMT_PREPARE` + `COM_STMT_EXECUTE` + `COM_STMT_CLOSE` 二进制协议（参数按 `Value` 绑定、结果按列类型解码）；
  - `COM_PING` / `COM_QUIT` / `COM_INIT_DB`。
- **显式不支持（报错，不静默降级）**：TLS（不发 `CLIENT_SSL`）、`caching_sha2` 完整鉴权（明文需 RSA，提示改用 `mysql_native_password`）、
  `CLIENT_MULTI_STATEMENTS`、`CLIENT_FOUND_ROWS`、压缩协议、LOCAL INFILE、预处理语句缓存。
  `CLIENT_FOUND_ROWS` 不开 = `affected_rows` 是「实际变更行数」，与 Rust `mysql` crate 默认能力集一致（已核对 `mysql-28.0.4/src/conn/mod.rs:777 get_client_flags`）。
- **值转换**：整数/浮点/Decimal/日期时间/BIT（大端→整数）/BLOB；`0000-00-00` 之类零值日期退化为文本不丢数据。

### 2. 验证（实测，非推测）

- 固定字节单测 **9 项**：握手解析、两种鉴权散列（含独立重算比对）、OK/ERR 包、文本行、二进制行（含 NULL 位图）、
  二进制日期时间 4/7/11 字节、lenenc 边界（250/251/65535/65536/2^24/2^64-1）、列定义。
- **回环端到端 1 项**：测试内起「脚本化假服务端」（真实 TCP 回环），覆盖握手 → 鉴权（**服务端按算法重算摘要并逐字节比对**）→
  `COM_QUERY` → 结果集（列定义/行/EOF）→ `COM_PING` → `COM_QUIT`。单跑确认未走 SKIP：`zig test src/zzig.zig --test-filter "端到端"` → `OK`。
- **⚠️ 顺带发现并修掉的老问题**：`zzig` 原有「模块内 test 块」**从来没被执行过** —— `zig build test` 报的 52 项其实是
  `test.zig` 的 25 项 + `xml-tests` 的 27 项，`db/sqlite.zig` 等模块测试全被漏掉。
  原因（实测）：`zig test` 只收集**同模块内被根文件直接 import** 的文件的 test 块，跨模块 `@import("zzig")` 不收集，
  `std.testing.refAllDecls` 也不收集。
  修法：`build.zig` 增加以 `src/zzig.zig` 为根的测试产物 `zzig-module-tests`，并在 `zzig.zig` 里加 `test { _ = @import("db/mysql.zig"); … }`。
  修正后 zzig 真实测试数 **52 → 79 项**，退出码 0。

### 3. 本仓接线

- `session.Session` 改为驱动联合：`Driver = union(enum) { sqlite: sqlite.Db, mysql: mysql.Conn }`；
  `init()` 保留原签名（SQLite）不破坏既有调用，新增 `initWithDriver()`。

- **用户原话**：「那你可以直接下载绿色版本到本地项目并持久保存用于后续测试」「zig的git要过滤」。
- **做法**：本机已有免安装版（`G:\Tools\mysql-portable\mysql-8.0.29-winx64`），不必再下载；
  新增 `tools/mysql-local.ps1`（setup/start/stop/status/reset）在**项目内**起独立实例：
  端口 3307、数据目录 `.tools\mysql\data-3307`（已 gitignore，重启后仍在），
  启动时用 `--init-file` 幂等建 `zcode_test` 库与 `root@'%'`、`zcode_native`、`zcode_sha2` 账号
  （`--initialize-insecure` 只建 `root@localhost`，从 127.0.0.1 走 TCP 会被 `ERROR 1130` 拒掉）。
- **实测修正（都有真库证据）**：
  1. **BLOB/TEXT 共用类型码**，必须按 `charset == 63` 判二进制，否则 TEXT 列被读成 Blob
     （现象：`Title` 显示 `[blob 12 字节]`）。
  2. **`caching_sha2_password` 完整鉴权用 PKCS#1 v1.5，不是 OAEP**：OAEP 产物能被 openssl 正确解出原文，
     但服务端回 `1045`；改 PKCS1 后立即登入成功。载荷 = `RSA( (password+'\0') XOR 握手 nonce )`。
  3. **BIT 线上为大端**：`BIT(16)` 存 `0x0102`，读回字节 `[0x01,0x02]` → 258；小端会得 513。
     即 **C# 绿色版该分支实现有误**，Rust 的大端与实测一致（已改回大端并用真库用例锁定）。
- **顺带修掉**：`parseHandshake` / `AuthSwitchRequest` 的插件名借用复用包缓冲 → 下一包即被覆盖（乱码），
  两处都改为拷贝；`closeQuietly` 在对端已断时不再因写 `COM_QUIT` 抛出 Windows 断连状态。
- **验证**：
  - `zzig`：`7/7 steps succeeded; 84/84 tests passed`；
  - 本仓真库（root/native）：`12/12 tests passed`，退出码 0；
  - 本仓真库（zcode_sha2，完整鉴权 RSA）：`12/12 tests passed`，退出码 0。

- **仍未做**：TLS（`CLIENT_SSL` 不发）、压缩协议、LOCAL INFILE、预处理语句缓存。

### 用户原话

### 决策：性能要有可复现数字，且不进 CI 门禁

**做了什么**：新增 `tools/bench.zig` + `zig build bench`（默认 `ReleaseFast`，`-Dbench-optimize` 可覆盖）。
每次运行前建全新临时库，避免上一轮残留数据影响唯一索引与计数。

**为什么这么做**：用户要求「性能上一定要保证」。此前所有结论都停留在「能跑通」，没有数字；
以后改 SQL 生成 / 缓存路径就无从判断是快了还是慢了。基准给出可对比的锚点，比口头保证有用。

**五组实测**（SQLite 内存库、ReleaseFast、批量提交，Windows / zig 0.17.1）：

| 用例 | 次数 | 总耗时 | 单次 |
|---|---|---|---|
| 实体 insert（含自增回写） | 500 | 3.77 ms | 7.53 µs |
| 批量 saveBatch（新增 2000 条） | 2000 | 4.40 ms | 2.20 µs/条 |
| findByPk（直连库，命中） | 2000 | 9.04 ms | 4.52 µs |
| 整表缓存 get（命中） | 20000 | 0.22 ms | 0.01 µs |
| 条件分页查询（10 行） | 300 | 4.49 ms | 14.96 µs |

读数含义：
- **缓存命中 0.01 µs** 说明整表缓存确实是「一次哈希查表」，不是每跳重建；
- **saveBatch 2.20 µs/条 vs 单条 insert 7.53 µs** 差 3.4 倍，主要来自单条每条一次自增回写 + 独立往返；
  批量走一条多值 INSERT，符合 C# `InsertBatch` 语义；
- **分页 14.96 µs 明显高于主键查 4.52 µs**，因为要走条件解析 + `COUNT(*)` + 两次往返，符合预期。

**基准不进门禁**：耗时随机器负载抖动（同轮并行跑别的构建能差 2 倍），做阈值判定只会制造假失败。
因此 `tools/regression.ps1` 不含 bench；改热路径后手动跑一次，与上表对比。

**踩坑**：初版 bench 用同一个 `bufPrint` 缓冲生成 Title，所有实体标题相同 → 撞唯一索引直接失败。
改为 `allocPrint` 到 arena，每个实体持有独立字符串。
