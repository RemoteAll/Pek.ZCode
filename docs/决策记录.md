## 2026-11-11 表归属连接的判定：`tableConn / tableBelongsToConn / tablesOfConn`

- **用户原话**：「C#的是不是ORM组件本身就会一起解析的，如果是的话，当前Rust和Zig版本的是不是也要有，而且更方便带出？」「需要的」
- **背景**：C# `DH.NCode` 解析 `Model.xml` 时就把 `TableItem.ConnName`（缺省用 `EntityModel.ConnName`）
  与 `Field.Description` 挂在实体上。Zig 侧 `model.zig` 本来已经按实体名/物理表名、属性名/`ColumnName` 反查，
  唯独**「这张表属于哪条连接」**要消费方自己写（表级优先、否则模型级）。
- **本轮新增**（与 Rust `Pek.RCode` 同名 API 语义逐条对齐）：
  - `EntityModel.modelConn()`：模型级连接名（缺省/空白 → null）；
  - `EntityModel.tableConn(meta)`：表**实际归属**的连接（表级优先，否则模型级；两级都没配 → null = 由调用方默认连接代管）；
  - `EntityModel.tableBelongsToConn(meta, conn)`：是否归属指定连接（忽略大小写；两级都没配视为归属）；
  - `EntityModel.tablesOfConn(gpa, conn)`：按连接取表（返回 `[]*const TableMeta`，调用方负责 `free`）。
- **注意**：参数名用 `meta` 而不是 `table` —— Zig 0.17 里参数名与方法名 `table` 冲突（`function parameter shadows declaration`）。
  `test` 块上也不能挂 `///` 文档注释（`documentation comments cannot be attached to tests`），用普通 `//`。
- **验证**：新增 `test "表归属连接：表级优先，否则模型级"`（表级优先 / 忽略大小写 / 按连接取表 / 两级都没配归调用方）；
  `zig build test --summary all` → **5/5 steps succeeded，test success**（unit + integration 全绿）。
- **配套**：Rust `Pek.RCode` 已提交 `9af228f`（`feat(model): 公开「表归属哪条连接」的判定`）。

## 2026-11-11（三）MySQL 绿色执行驱动 + 单对象缓存 + 生产模型回归

- **用户原话**：
  - 「**MySQL 执行驱动** 不是说了参考Rust有一个绿色版本么？」（前一轮我把 MySQL 列为「必须先要连接串」的候选，用户指出 Rust 侧本来就是**纯协议绿色实现**，不需要本地库也能做）。
  - 「把 `zzig` 的 2 个本地提交 这个已经提交了」（zzig 两个提交已推送完毕，本轮从 `origin/main` 起算）。
- **结论**：MySQL 走**纯 wire protocol**（不加载 `libmysqlclient`），落在公共库 `zzig.db.mysql`，本仓只做方言/会话接线。

### 1. 新增 `zzig.db.mysql`（绿色驱动）

- **为什么在 zzig**：与 `zzig.db.sqlite` 同级，任何项目都能复用；本仓不复制实现。
- **协议覆盖**：
  - 握手 v10 解析（capability 高低位、scramble 分两段、插件名）；
  - `mysql_native_password`（完整）+ `caching_sha2_password`（**仅 fast auth**）；
  - `COM_QUERY` 文本协议（DDL / 无参查询）；
  - `COM_STMT_PREPARE` + `COM_STMT_EXECUTE` + `COM_STMT_CLOSE` 二进制协议（参数按 `Value` 绑定、结果按列类型解码）；
  - `COM_PING` / `COM_QUIT` / `COM_INIT_DB`。
- **显式不支持（报错，不静默降级）**：TLS（不发 `CLIENT_SSL`）、`caching_sha2` 完整鉴权（明文需 RSA，提示改用 `mysql_native_password`）、
  `CLIENT_MULTI_STATEMENTS`、`CLIENT_FOUND_ROWS`、压缩协议、LOCAL INFILE、预处理语句缓存。
  `CLIENT_FOUND_ROWS` 不开 = `affected_rows` 是「实际变更行数」，与 Rust `mysql` crate 默认能力集一致（已核对 `mysql-28.0.4/src/conn/mod.rs:777 get_client_flags`）。
- **值转换**：整数/浮点/Decimal/日期时间/BIT（大端→整数）/BLOB；`0000-00-00` 之类零值日期退化为文本不丢数据。

### 2. 验证（实测，非推测）

- 固定字节单测 **9 项**：握手解析、两种鉴权散列（含独立重算比对）、OK/ERR 包、文本行、二进制行（含 NULL 位图）、
  二进制日期时间 4/7/11 字节、lenenc 边界（250/251/65535/65536/2^24/2^64-1）、列定义。
- **回环端到端 1 项**：测试内起「脚本化假服务端」（真实 TCP 回环），覆盖握手 → 鉴权（**服务端按算法重算摘要并逐字节比对**）→
  `COM_QUERY` → 结果集（列定义/行/EOF）→ `COM_PING` → `COM_QUIT`。单跑确认未走 SKIP：`zig test src/zzig.zig --test-filter "端到端"` → `OK`。
- **⚠️ 顺带发现并修掉的老问题**：`zzig` 原有「模块内 test 块」**从来没被执行过** —— `zig build test` 报的 52 项其实是
  `test.zig` 的 25 项 + `xml-tests` 的 27 项，`db/sqlite.zig` 等模块测试全被漏掉。
  原因（实测）：`zig test` 只收集**同模块内被根文件直接 import** 的文件的 test 块，跨模块 `@import("zzig")` 不收集，
  `std.testing.refAllDecls` 也不收集。
  修法：`build.zig` 增加以 `src/zzig.zig` 为根的测试产物 `zzig-module-tests`，并在 `zzig.zig` 里加 `test { _ = @import("db/mysql.zig"); … }`。
  修正后 zzig 真实测试数 **52 → 79 项**，退出码 0。

### 3. 本仓接线

### 先划范围：什么叫「全量」

对照两套参考实现（C# `DH.NCode` 约 3 MB、Rust `Pek.RCode/src` 约 1.3 MB）逐模块过了一遍，

### 迁移 `Full`：删列删索引，且**先删索引再删列**

- `On` 仍只做创建类动作（建表/补列/建索引），**不删任何东西**。
- `Full` 才允许删除：模型里没有的列与索引。
- 表级 `<Table Migration="X">` 只能**收紧**（`min(表级, 全局)`），与 C# `ResolveMigration` 一致。
- **踩到的坑**：先删列会报 `error in index ix_legacy after drop column: no such column: Legacy`
  —— 独立索引引用了该列。顺序改成「先删索引、再删列」后通过。
- 仍未做：**改列类型/长度**（SQLite 需整表重建，MySQL 要 `MODIFY`），已在对照表写明。

### 性能调优：SQLite 预处理语句缓存（本轮唯一的代码级优化）

**做了什么**：`Session` 增加按 SQL 文本的语句缓存（上限 64 条，默认开）。
命中后 `reset()` + 重新绑定即可复用，省掉每次 `prepare`/`finalize`。

**实测（同机、同一轮内、SQLite 内存库、ReleaseFast，`zig build bench`）**：

### 踩坑清单（下次别重复）

1. **`Dal` 按值返回 + 在其中先开会话 = 悬空指针**：`db.lib` 指向 `Dal.lib`，

2. **测试用 `db2`/`m` 不可变时 `deinit` 编译不过**（`*EntityModel` 非 const）。
3. **`{d:0>4}` 在 Zig 0.17 会带出多余符号位**（`2024` → `+2024`）：日期补零一律手写。
4. **内联 `allocPrint(..., .{try quoteAlloc(...)})` 会漏内存**：先取变量再 `defer free`。
5. **查询结果统一归会话 arena**：`children`/`roots`/`descendants`/`pathToRoot` 都返回 arena 切片，

## 2026-11-11（十）MySQL `LOAD DATA LOCAL INFILE` 批量装载：实测快 4 倍

### 用户原话
> 「请继续，先做功能全量迁移，然后再做性能调优」

### 功能：LOCAL INFILE（此前明确列为「不支持」的能力）

**驱动层**（`zzig/src/db/mysql.zig`）：
- 握手时声明 `CLIENT_LOCAL_FILES`（仍按服务端 capability 取交集，服务端不支持就不声明）；
- `Conn.loadDataLocal(sql, data)`：发 `COM_QUERY` → 等服务端 `0xfb` 请求 → **客户端流式发送数据**
  → 空包结束 → 读 OK。数据**不落盘、不需要服务端文件权限**（这是 LOCAL 的含义）。
- 分块：每包 ≤ `max_payload`，结束时单独发一个空包。为此新增 `writeRawPacket`（只发一个包、不自动补终止包）——
  用原来的 `writePacket` 会在「数据正好是 16MB 整数倍」时**提前截断**，这类坑只在超大数据量才暴露。
- 失败**不降级**：没协商上能力 → `error.LocalInfileNotSupported`；服务端 `local_infile=OFF`（MySQL 8 默认）
  → 服务端回 3948，按 `error.Server` 抛且 `lastError()` 带原文。

**表级 API**（`src/dbtable.zig`）：`TableRef.loadDataBatch(session, columns, rows)`
- `columns` 为物理列名、与每行值一一对应；NULL 写成 `\N`；`\\`/`\t`/`\n`/`\r`/`\0` 按 MySQL 默认转义；
- 二进制列（`Value.blob`）**直接报 `error.Unsupported`**（文本装载无法安全表达任意字节，绝不静默截断）；
- 非 MySQL 方言返回 `error.Unsupported`，调用方回落 `insertBatch`（不假装支持）。

**验证**：
- 回环假服务端：断言客户端**声明了** `CLIENT_LOCAL_FILES`、`0xfb` 之后按序收到数据包、内容与期望逐字节一致、空包结束。
- 真库（本机 3307 / MySQL 8.0.29）：5000 行装载 → 影响行数 5000 → `count` 5000；
  其中一行含 **Tab / 换行 / 反斜杠 / 中文**，读回来逐字节一致；另一行 `Amount` 为 NULL，读回来仍是 NULL（不是空串）。

### 性能：同机同轮对比（`zig build bench-mysql`，20000 行 × 5 列）

| 方式 | 第 1 次 | 第 2 次 | 每行 |
|---|---|---|---|
| `insertBatch`（多行 INSERT，5000 行/批） | 897.45 ms / 22,285 行/秒 | 732.73 ms / 27,295 行/秒 | 44.87 / 36.64 µs |
| `loadDataBatch`（LOCAL INFILE） | **224.27 ms / 89,178 行/秒** | **194.02 ms / 103,081 行/秒** | **11.21 / 9.70 µs** |

**结论：约 3.8~4.0 倍**（每行 36~45 µs → 9.7~11.2 µs），两次取样一致，不是抖动。

**为什么差这么多**（不是玄学）：多行 INSERT 让服务端**逐行做 SQL 语法分析 + 表达式求值 + 参数绑定**，
20000 行就是 20000 次解析；`LOCAL INFILE` 走的是**行式解析器**（按分隔符切列），几乎没有语法开销。
批量越大差距越明显——这正是 C# 侧 `DH.MySql` 也支持 `MySqlBulkLoader` 的原因。

**用法建议**（写进 README）：
- 万行以上的日志/采集/导入：`loadDataBatch`；
- 百行级或需要逐行自增 ID：`insertBatch` / `saveBatch`；
- `loadDataBatch` 不返回每行自增 ID（LOAD DATA 语义如此）。

### 踩坑

1. **假服务端必须声明 `CLIENT_LOCAL_FILES`**：客户端按「服务端 capability ∩ 客户端期望」取交集，
   服务端不声明就会被裁掉；表现是握手后立刻断（客户端等下一条包，服务端已退出）。
2. **`writePacket` 的自动补空包会截断 LOCAL INFILE 数据**（见上）→ 单独实现 `writeRawPacket`。
3. 编辑工具的一次「删空行」把 `/// 文档注释` 与 `pub fn ...` 挤到同一行，导致函数体被解析成结构体字段
   （报 `declarations are not allowed between container fields`）。改源码时**别用正则式整段替换**，
   落盘后跑一次 `zig build` 立刻能发现。

## 2026-11-11（十一）MySQL TLS：补齐 `SslMode` 五档（含 std 不支持 `CertificateRequest` 的处理）

### 用户原话
> 「请继续，先做功能全量迁移，然后再做性能调优」

上一轮收尾时我列了剩余四项并建议先做「预处理语句复用」（性能项），用户重申**先功能后性能** →
本轮取「MySQL TLS」这项硬功能缺口：此前的驱动**根本不发 `CLIENT_SSL`**，
连 `require_secure_transport=ON` 的库都连不上，属于「有功能缺口」而不是「性能不够」。

### 做了什么

**驱动层（`zzig/src/db/mysql.zig`）**
- 新增 `SslMode`：`disabled | preferred | required | verify_ca | verify_full`（与 MySqlConnector 同口径，
  `None` 等价 `Disabled`；取值认不出由上层报 `error.InvalidSslMode`，**绝不静默按缺省走**）。
- 握手按协议插入 `SSLRequest`（32 字节：能力位 + 最大包长 + 字符集 + 23 个 0，序号与握手连续），
  随后在**同一条 TCP** 上升级为 TLS，再在 TLS 上发正式的 `HandshakeResponse41`。
- 缺省 `SslMode=Preferred`：服务端支持就加密；TLS 握手失败则**整条连接回退明文重连一次**，
  并把第一次的失败原因打到 stderr（不静默降级）。
- 收发层抽象出 TLS 分支：写侧「TLS 加密 → socket Writer」两级 flush（一个 MySQL 包 = 4 字节头 + 载荷
  两次 `writeAll`，中途 flush 会多一个 TLS record）；读侧走 TLS Reader。
- 读侧**必须循环**：TLS 层返回 0 字节不等于对端关闭 —— 可能只是消费了 `NewSessionTicket` / `KeyUpdate`
  这类控制记录；只有 `EndOfStream` 或 `close_notify` 才算关闭（见下「踩坑 4」）。
- `TlsState` **堆分配**：`std.crypto.tls.Client` 内部持有 Reader/Writer 指针，而 `Conn` 是按值返回的，
  栈上地址会随复制失效。

**连接串（`src/dal.zig`）**：认 `SslMode` / `SSL Mode`、`SslCa` / `CertificateFile` / `SslCert`；
根证书支持绝对路径与相对当前目录两种；`verify_ca`/`verify_full` 未给 `SslCa` 时用系统根证书
（Windows 证书库 / Linux 常见 CA 目录），空证书束直接报错。

### 关键决策：供应商化一份 TLS 客户端（`zzig/src/db/tls_client.zig`）

**为什么**：MySQL 8 只要服务端配了 `ssl_ca`（`--initialize` 自动生成证书的**默认**形态就是如此），
TLS 1.3 握手会发 `CertificateRequest(0x0d)`。std 的 TLS 客户端对该消息走 `else => error.TlsUnexpectedMessage`，
于是**连默认 MySQL 8 的 TLS 都连不上**（不是「部分场景不可用」，而是「几乎全部 MySQL 8 不可用」）。

**怎么做的**：把 std 的 `Client.zig` 复制进 zzig，只加三处（其余逐字未改，便于日后 diff）：
1. `.certificate_request` 分支：计 transcript、置 `cert_requested`（TLS 1.2 的该消息格式不同 → 明确报错，不猜）；
2. 客户端飞行里补一条**空的** Certificate（TLS 1.3 §4.4.2 允许空列表），
   并用 client handshake key 的正确序号加密（首条 = 0，Finished = 1）；
3. 该空消息按协议顺序计入 transcript，客户端 Finished 的校验值才对。

**边界**：不支持客户端证书（双向 TLS 的 mTLS 场景仍未做），但「服务端要求出示证书」时回空列表即可通过
（MySQL 用 `SSL_VERIFY_PEER`，只有 `REQUIRE X509` 才会强制）。**std 支持后应整个文件删掉**。

### 踩坑（都有实测证据，不是猜）

1. **`SSLRequest` 之后服务端会「静默 10 秒」再回 `ER_HANDSHAKE_ERROR(1043) Bad handshake`**：
   用探针逐条打印等待时长，5 个变体全部 **10 000~10 015 ms** → 那是握手超时，
   说明服务端**已经进入 TLS** 在等 ClientHello，而不是「拒绝了 SSLRequest」。
   一开始把 26 字节的错误包当成「服务端拒绝」，方向错了。
2. **协议形态是裸 TLS，不是「TLS 装在 MySQL 包里」**：先用 Python 的 `ssl.wrap_socket` 直连验证；
   再用 TCP 代理抓 `mysql.exe --ssl-mode=REQUIRED` 的真实字节，确认 `SSLRequest` 之后紧跟 `16 03 01 ...`。
3. **std 报 `TlsUnexpectedMessage` 但不告诉你在哪**：把 std 的 `Client.zig` 复制到本地并给每个
   `return error.TlsUnexpectedMessage` 打点，才定位到「未处理的握手类型 0x0d」。
   注意 `else => return error.X,`（逗号）这种写法用「按分号替换」是抓不到的，得单独处理。
4. **TLS 读返回 0 不等于 EOF**：`NewSessionTicket` 会被 TLS 层消费掉而不产生应用数据，
   此时 `readVec` 返回 0；按「0 = 对端关闭」处理会得到假的 `ConnectionClosed`。
   现在改成循环读，只有 `EndOfStream` / `close_notify` 才算关闭（修好后 `Ssl_cipher` 立刻有值）。
5. **`finalResult()` 是破坏性操作**：它内部会写 padding、改哈希状态。想「先取一份 hash 再用」
   必须用 `peek()`（内部复制一份再 final）；用 `finalResult` 取快照会让后续 transcript 全错 →
   服务端回 `decrypt_error`。
6. **进 transcript 的是握手消息本身**，不含 TLS 1.3 记录尾部那个「内层内容类型」字节；
   把它算进去同样会 `decrypt_error`。
7. **证书链坑**：MySQL 自动生成的 server 证书 CN 是本机生成的随机名，`VerifyFull` 连 `127.0.0.1`
   必然 `CertificateHostMismatch`；自签 CA 场景正确档位是 `VerifyCA`（校链不校主机名）。

### 验证（真库，MySQL 8.0.29 @ 3307）

```
[mysql-tls] Required cipher = "TLS_AES_128_GCM_SHA256"
[mysql-tls] None cipher = ""                                  ← 明文档确实是明文
[mysql-tls] VerifyCA（无 CA）按预期失败：TlsCertificateNotVerified   ← 不校验证书就必须连不上
[mysql-tls] VerifyCA(ca) cipher = "TLS_AES_128_GCM_SHA256"
[mysql-tls] VerifyFull 按预期失败（主机名不匹配）：CertificateHostMismatch
```

- `zig build test`：**110/110**（单元 74 + 集成 36）；真库 `-Dmysql-conn -Dmysql-ca` → **36/36**，无泄漏。
- zzig：**70/70**（含 PG 回环、LOCAL INFILE、TLS）。
- `tools/regression.ps1`：**PASSED**。

## 2026-11-11（十二）MySQL 压缩协议（`CLIENT_COMPRESS`）：TLS/压缩两个传输缺口都补齐

### 用户原话
> 「请继续，先做功能全量迁移，然后再做性能调优」

上一轮把 TLS 做完后，「MySQL TLS/压缩」只剩压缩这一半；本轮收掉它，MySQL 驱动的传输层能力就完整了。

### 做了什么

**驱动层（`zzig/src/db/mysql.zig`）**
- 握手按 `opts.compress` 声明 `CLIENT_COMPRESS`；**认证 OK 之后**才切到压缩（协议规定，OK 本身不压）。
- 压缩帧格式：`{3 字节压缩后长度, 1 字节压缩序号, 3 字节解压后长度}` + 数据；解压后长度写 0 表示本帧未压缩。
- 两条独立计数器：内层包序号 `seq`、压缩帧序号 `compress_seq`；每发一条新命令两者都归零（与协议一致），
  读响应时都从对端包头取值再 +1（读写共用一个序列）。
- **写侧**：内层 4 字节头 + 载荷先攒进 `wbuf`，一次 flush 时按 ≤16MB 切帧压缩；
  小于 50 字节的帧、以及压完反而更大的帧，按未压缩形态发（否则小包越压越大）。
- **读侧**：压缩帧解压进 `rbuf`，再按内层 4 字节头切包；已消费部分及时前移避免缓冲膨胀。
- 未压缩路径**完全不变**（缺省关闭），走的是原来那套 `writePacket`/`readPacket`。

**连接串（`src/dal.zig`）**：认 `Compression` / `Compress` / `UseCompression`（`parseBool`，认 `true/1/yes`）。
服务端没声明 `CLIENT_COMPRESS` 时**打印一行说明**并继续未压缩运行 —— 不静默假装压缩了。

### 踩坑

1. **`flate.Compress.init` 断言输出 Writer 缓冲 > 8 字节**：用空的 `Writer.Allocating` 直接 panic。
   改成 `Allocating.initCapacity(gpa, 4096)`。
2. **`packed` 是 Zig 关键字**：测试里拿它当变量名直接语法错（`expected 'an identifier', found 'packed'`）。
3. **测试载荷不能按字节切 UTF-8**：按 `i % 18` 切「多字节内容-test」会切出半个汉字，
   MySQL 直接回 `1366 Incorrect string value`（这条错本身也证明了压缩流里的错误包能被正确解析）。
   改成按完整 3 字节汉字填充、余数补 ASCII。

### 为什么先做这一项（以及为什么没继续做功能项）

| 剩余功能项 | 阻塞点（实测） |
|---|---|
| SQL Server（TDS）驱动 | `127.0.0.1:1433` 不可连、`Get-Service MSSQL*` 无实例、`docker` 未安装 → **没有真库**，只能对着自己写的假服务端测，按「不能猜」的规矩不敢声称可用 |

| Oracle（OCI/TNS） | 同上，且更冷门 |

于是转性能阶段（用户原本定的第二步），从**最确定的热点**入手：带参语句每次都在
`COM_STMT_PREPARE` → `COM_STMT_EXECUTE` → `COM_STMT_CLOSE` 三步走，prepared 句柄完全没复用。

### 做了什么

`zzig/src/db/mysql.zig`：`Conn` 增加预处理语句缓存
- 键 = SQL 文本；值 = `{句柄 id, 列数, 参数数, SQL 副本}`。SQL 副本**自己持有**（不借 arena，
  否则下次 `resetResults` 就悬空）。
- 上限默认 32 条，满了按 **FIFO** 淘汰最旧的一条（热点语句很快稳定，LRU 的收益不值得复杂度）。
- `setStmtCacheLimit(0)` 关闭缓存（同一个进程里做 A/B 用）；`stmtCacheStats()` 给命中/未命中原语。
- `deinit` 先 `clearStmtCache()`（逐条发 `COM_STMT_CLOSE`）再 `COM_QUIT`，并把缓存链表自身的
  缓冲一并释放（**这里踩过**：只清条目不 `deinit` 链表 → 每条连接泄漏 144 字节，真库用例当场抓到）。
- 执行失败**不**清缓存：MySQL 允许错误后继续复用同一句柄（缓存键仍是同一条 SQL）。
- 注意 prepared 句柄是**连接私有**的，所以缓存挂在 `Conn` 上、断线重连自然失效。

### 实测（同一进程内 A/B，`zig build bench-mysql`，3000 次，本机 3307）

| 场景 | 未复用 | 复用 | 提速 |
|---|---|---|---|
| 单参数点查（`WHERE Id = ?`） | 843.48 ms（281.16 µs/行） | 514.38 ms（171.46 µs/行） | **1.64×** |
| 单参数插入（同一事务内） | 932.02 ms（310.67 µs/行） | 574.39 ms（191.46 µs/行） | **1.62×** |

口径说明：
- 两轮在**同一进程、同一连接、同一数据**上顺序跑，先关缓存再开缓存，避免跨轮次相减
  （本机跨轮次绝对值可差 20%+，之前踩过）；
- 插人在一个事务里跑，避免把「每次提交」的 fsync 开销算进协议对比；
- 点查与插人都**热身一次**，把首次 prepare 排除在计时外。

## 2026-11-11（十四）功能迁移续轮：数据库远程服务 `DbService` / `DbClient`（HTTP/1.1 + JSON）

### 用户原话
> 「先不管是否缺，先把功能做迁移，远程服务 DbService这个是能实现的吧」

（同轮更早还问过：「我另外想知道数据库连接是HTTP1.1还是HTTP2.0的？」）

### 先回答 HTTP 版本这个问题（有源码证据，不是印象）
- 本仓 / `zzig` 的客户端走的是 **HTTP/1.1**。之前查过 std 的 HTTP 模块：
  `std/http.zig:13` 里 `Version = enum { @"HTTP/1.0", @"HTTP/1.1" }`，整个 std 里**没有 h2 实现**；
  Rust 侧的参考实现用 `ureq 3.4.2`，同样是 1.1。
- 结论：**数据库连接（MySQL/PostgreSQL/TDS-未做/OCI-未做）是各自的原生二进制协议，不是 HTTP**；
  「HTTP/1.1 还是 2.0」这个问题只对**远程服务那一层**成立，而那一层现在是 1.1。

### 做了什么

1. **`zzig/src/http/server.zig`（新，zzig 提交 `e227114`）**：极简 HTTP/1.1 服务端
   - `Server.init(gpa, io, ctx, handler, .{ .max_body, .max_connections })` + `run(host, port)`（阻塞 accept，每连接一个线程）
   - `RequestView{method,target,path,query,body}` / `Reply{status,body,content_type}`
   - `serveOne`：`Content-Length` 超上限**在读 body 前**就回 413；handler 出错回 500 并打日志
   - 端到端实测：子线程起服务 + 主线程当客户端，收到 113 字节响应（当时 zzig 模块测试 47 项全过）

2. **`Pek.ZCode/src/dbservice.zig`**：把本进程的 `Dal` 暴露成 HTTP 路由
   - `Db/Login` / `Db/Query` / `Db/Execute` / `Db/InsertAndGetIdentity` / `Db/QueryCount` /
     `Db/GetTables` / `Db/Begin` / `Db/Commit` / `Db/Rollback`
   - 统一信封 `{code, data, msg}`（`code=0` 成功），令牌从 JSON `token` 字段或 `?token=` 取
   - 参数是**键值字典**，服务端**按键名字母序**绑定（与 Rust 版口径一致，不依赖调用方顺序）
   - 事务：`Db/Begin` 取一条独立会话并 `BEGIN`，之后带 `tx` 的语句路由回该会话；空闲超时（默认 60 s）
     自动回滚回收；清扫**惰性**做（≤1 次/秒），不额外起定时器

3. **`Pek.ZCode/src/dbclient.zig`**：客户端
   - `login / query / queryTx / execute / executeTx / insertAndGetIdentity / beginTx / commitTx / rollbackTx`
   - `code=401` → `error.Unauthorized`，**404 → `error.Unsupported`**（服务端没这条路由时客户端据此降级），
     其余非 0 → `error.Server`，服务端 `msg` 落在 `lastError()`

### 踩到的四个坑（都实测，不是推测）

1. **`Session` 不能按值搬动**：`Session.stmt_cache` 里的 `Stmt` 指回 `session.driver.sqlite`。
   `beginTx` 里先把 `var s = try openSession()` 再 `slot.* = .{ .session = s }` →
   栈上临时变量出作用域后指针悬空，`rollback` 回收会话时 `sqlite3_finalize` **段错误（地址 0x40）**。
   修法：事务会话一律 `gpa.create(Session)` 后再往里放，之后不再搬；`TxSlot.session` 改成 `*Session`。
2. **事务里的语句必须带 `tx`**：最初 `Db/Execute` 不看 `tx`，于是「BEGIN 之后的 INSERT」落在**新会话**，
   回滚自然不生效（用例的期望值当时是对的，是我实现漏了）。补 `acquire()`：带 `tx` 复用事务会话，
   不带才新开；客户端补 `queryTx` / `executeTx`。
3. **`login` 发的是字面量 `"null"`**：服务端解析 JSON 拿不到 `token` → 必然 401。
   改成发完整请求体（`{db,token}`）。
4. **关监听不能直接 `deinit`**：服务端线程阻塞在 `accept` 时关监听，std 走 `.CANCELLED => unreachable`
   直接 panic。正确收尾：先 `stop=true`，再**自连接一次**把 accept 唤醒，`join` 之后才 `deinit`。

### 与 C# 的已知差异（不静默降级，已写进 `docs/移植对照-NCode.md`）
C# `DbController.Query` 的应答是 **`DbTable` v3 二进制**（`rs.ToPacket()`），本实现返回 **JSON 行列**。
所以「C# 客户端 ↔ Zig 服务端」调 `Db/Query` **不互通**，其余路由是 JSON 信封可以互通。
要二进制互通得再补 `DbTable` v3 编解码（本轮没做）。

### 实测踩到的坑（都是真跑出来的，不是推测）

1. **`MODIFY COLUMN` / `ALTER COLUMN` 是「整列定义替换」**：只写类型会**把 NOT NULL 悄悄去掉**
   （MySQL 8.0.29 真库实测：改完后 `is_nullable` 从 NO 变 YES）。现在语句里必须带 `NOT NULL`/`NULL`
   （MySQL/Oracle 还要带 `DEFAULT`、`COMMENT`），并加了真库断言守住。
2. **PLP 不能按「总长」直接 take**：线上是 `总长(8) + [块长(4)+块]* + 0(4)`，直接取 total 字节会把块长当正文，
   整条令牌流从此错位（表现为后面某个 INTN 长度不是 1/2/4/8 → `error.Protocol`）。
3. **DATETIME2 的值是「时间 5 字节在前、日期 3 字节在后」**；假服务端写成「日期在前」时，客户端仍能读出 8 字节，
   但解码结果变成 2024-02-02（月份断言先炸才发现）。
4. **DECIMALN 的长度字节含符号位**：`符号(1) + magnitude(N)` → 长度要写 `1+N`。
5. **SQLite 重建时索引名是库内全局唯一**：旧表还在就建同名索引会直接报
   `index ix_xxx already exists` → 顺序必须是「建表 → 搬数据 → 删旧表 → 建索引」。
6. **`[_]u8{0} ** N` 在 0.17.1 直接编译报错**（解析成两个 `*`）；`std.posix.getenv` 也已不存在。
7. **`accept` 阻塞时不能直接 `deinit` 监听**（std `.CANCELLED => unreachable` panic）——dbservice 那轮的坑，
   这次在 TDS 回环用例里又差点踩到，已改成「自连一次唤醒 → join → deinit」。
8. **用 PowerShell 改源码会把中文写坏**（`Get-Content -Raw` 按 ANSI 读 UTF-8 → 回写即乱码）：
   本次真踩到一个新建的测试文件（已整文件重写）。纪律再确认：**源码/文档只用编辑工具改**。

### 实测出来的三个反直觉点（都不在文档里，只能靠跑）

- **浮点是大端**：`Binary.IsLittleEndian` 默认 `false` → `Write(Double)` 走 `WriteDoubleBigEndian`
  （1.5 → `3F F8 00 00 00 00 00 00`）。按“小端”猜会全错。
- **整型一律 7bit 变长**，包括 `Decimal.GetBits()` 的四个 32 位分量、`DateTime.ToBinary()`；
  而**行数是 4 字节小端**（`Total.GetBytes()` 原样写，不走 `Write`）。
- **C# 写 null 会抛异常**：`BinaryGeneral.Write(value, type)` 对值类型列执行 `(Int64)(value ?? 0)`，
  而 `value ?? 0` 是装箱的 **Int32** 0 → 拆箱成 Int64 直接 `InvalidCastException`。
  它自己读库时又把 `DBNull` 换成类型默认值 → 本实现与之一致：NULL 写成默认值。

### 做了什么

- **`src/dbtable_packet.zig`（新）**：`encodeAlloc` / `encodeRowsAlloc` / `decodeAlloc`
  + `inferColumnType`（按每列第一个非 NULL 值定类型；全 NULL → string；`Decimal` 超出 96 位尾数/28 位小数
  自动降级为 string，避免溢出）。
- **`Db/Query?format=packet`（也认 `v3`/`binary`）**：返回裸二进制 + `Content-Type: application/x-db-table; version=3`；
  **默认仍是 JSON**（不改旧行为）。错误路径仍回 JSON 信封，客户端据此报错。
- **`DbClient.queryPacket`**：请求 packet 并解码；解失败时把响应开头 200 字节打进 `lastError`。
- zzig 侧补 `DateTime.daysSinceUnixEpoch()` / `toUnixSeconds()`（.NET ticks 换算需要，与 `fromUnixSeconds` 互逆，带单测）。

### 验证（实测输出）

- `src/dbtable_packet.zig` 单测 **5 项全过**：8 列 168 字节与 C# 输出**逐字节相同**（含中文、负数、decimal、
  datetime、byte[]、空串），11 种单列 TypeCode 探测逐字节相同，黄金字节可解回原值，
  NULL 按默认值落字节，坏魔数/未知 TypeCode 明确报错。
