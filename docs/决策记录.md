## 2026-11-11 表归属连接的判定：`tableConn / tableBelongsToConn / tablesOfConn`

- **用户原话**：「C#的是不是ORM组件本身就会一起解析的，如果是的话，当前Rust和Zig版本的是不是也要有，而且更方便带出？」「需要的」
- **背景**：C# `DH.NCode` 解析 `Model.xml` 时就把 `TableItem.ConnName`（缺省用 `EntityModel.ConnName`）
  与 `Field.Description` 挂在实体上。Zig 侧 `model.zig` 本来已经按实体名/物理表名、属性名/`ColumnName` 反查，
  唯独**「这张表属于哪条连接」**要消费方自己写（表级优先、否则模型级）。
- **本轮新增**（与 Rust `Pek.RCode` 同名 API 语义逐条对齐）：
  - `EntityModel.modelConn()`：模型级连接名（缺省/空白 → null）；
  - `EntityModel.tableConn(meta)`：表**实际归属**的连接（表级优先，否则模型级；两级都没配 → null = 由调用方默认连接代管）；
  - `EntityModel.tableBelongsToConn(meta, conn)`：是否归属指定连接（忽略大小写；两级都没配视为归属）；
  - `EntityModel.tablesOfConn(gpa, conn)`：按连接取表（返回 `[]*const TableMeta`，调用方负责 `free`）。
- **注意**：参数名用 `meta` 而不是 `table` —— Zig 0.17 里参数名与方法名 `table` 冲突（`function parameter shadows declaration`）。
  `test` 块上也不能挂 `///` 文档注释（`documentation comments cannot be attached to tests`），用普通 `//`。
- **验证**：新增 `test "表归属连接：表级优先，否则模型级"`（表级优先 / 忽略大小写 / 按连接取表 / 两级都没配归调用方）；
  `zig build test --summary all` → **5/5 steps succeeded，test success**（unit + integration 全绿）。
- **配套**：Rust `Pek.RCode` 已提交 `9af228f`（`feat(model): 公开「表归属哪条连接」的判定`）。

## 2026-11-11（三）MySQL 绿色执行驱动 + 单对象缓存 + 生产模型回归

- **用户原话**：
  - 「**MySQL 执行驱动** 不是说了参考Rust有一个绿色版本么？」（前一轮我把 MySQL 列为「必须先要连接串」的候选，用户指出 Rust 侧本来就是**纯协议绿色实现**，不需要本地库也能做）。
  - 「把 `zzig` 的 2 个本地提交 这个已经提交了」（zzig 两个提交已推送完毕，本轮从 `origin/main` 起算）。
- **结论**：MySQL 走**纯 wire protocol**（不加载 `libmysqlclient`），落在公共库 `zzig.db.mysql`，本仓只做方言/会话接线。

### 1. 新增 `zzig.db.mysql`（绿色驱动）

- **为什么在 zzig**：与 `zzig.db.sqlite` 同级，任何项目都能复用；本仓不复制实现。
- **协议覆盖**：
  - 握手 v10 解析（capability 高低位、scramble 分两段、插件名）；
  - `mysql_native_password`（完整）+ `caching_sha2_password`（**仅 fast auth**）；
  - `COM_QUERY` 文本协议（DDL / 无参查询）；
  - `COM_STMT_PREPARE` + `COM_STMT_EXECUTE` + `COM_STMT_CLOSE` 二进制协议（参数按 `Value` 绑定、结果按列类型解码）；
  - `COM_PING` / `COM_QUIT` / `COM_INIT_DB`。
- **显式不支持（报错，不静默降级）**：TLS（不发 `CLIENT_SSL`）、`caching_sha2` 完整鉴权（明文需 RSA，提示改用 `mysql_native_password`）、
  `CLIENT_MULTI_STATEMENTS`、`CLIENT_FOUND_ROWS`、压缩协议、LOCAL INFILE、预处理语句缓存。
  `CLIENT_FOUND_ROWS` 不开 = `affected_rows` 是「实际变更行数」，与 Rust `mysql` crate 默认能力集一致（已核对 `mysql-28.0.4/src/conn/mod.rs:777 get_client_flags`）。
- **值转换**：整数/浮点/Decimal/日期时间/BIT（大端→整数）/BLOB；`0000-00-00` 之类零值日期退化为文本不丢数据。

### 2. 验证（实测，非推测）

- 固定字节单测 **9 项**：握手解析、两种鉴权散列（含独立重算比对）、OK/ERR 包、文本行、二进制行（含 NULL 位图）、
  二进制日期时间 4/7/11 字节、lenenc 边界（250/251/65535/65536/2^24/2^64-1）、列定义。
- **回环端到端 1 项**：测试内起「脚本化假服务端」（真实 TCP 回环），覆盖握手 → 鉴权（**服务端按算法重算摘要并逐字节比对**）→
  `COM_QUERY` → 结果集（列定义/行/EOF）→ `COM_PING` → `COM_QUIT`。单跑确认未走 SKIP：`zig test src/zzig.zig --test-filter "端到端"` → `OK`。
- **⚠️ 顺带发现并修掉的老问题**：`zzig` 原有「模块内 test 块」**从来没被执行过** —— `zig build test` 报的 52 项其实是
  `test.zig` 的 25 项 + `xml-tests` 的 27 项，`db/sqlite.zig` 等模块测试全被漏掉。
  原因（实测）：`zig test` 只收集**同模块内被根文件直接 import** 的文件的 test 块，跨模块 `@import("zzig")` 不收集，
  `std.testing.refAllDecls` 也不收集。
  修法：`build.zig` 增加以 `src/zzig.zig` 为根的测试产物 `zzig-module-tests`，并在 `zzig.zig` 里加 `test { _ = @import("db/mysql.zig"); … }`。
  修正后 zzig 真实测试数 **52 → 79 项**，退出码 0。

### 3. 本仓接线

### 先划范围：什么叫「全量」

对照两套参考实现（C# `DH.NCode` 约 3 MB、Rust `Pek.RCode/src` 约 1.3 MB）逐模块过了一遍，

### 迁移 `Full`：删列删索引，且**先删索引再删列**

- `On` 仍只做创建类动作（建表/补列/建索引），**不删任何东西**。
- `Full` 才允许删除：模型里没有的列与索引。
- 表级 `<Table Migration="X">` 只能**收紧**（`min(表级, 全局)`），与 C# `ResolveMigration` 一致。
- **踩到的坑**：先删列会报 `error in index ix_legacy after drop column: no such column: Legacy`
  —— 独立索引引用了该列。顺序改成「先删索引、再删列」后通过。
- 仍未做：**改列类型/长度**（SQLite 需整表重建，MySQL 要 `MODIFY`），已在对照表写明。

### 性能调优：SQLite 预处理语句缓存（本轮唯一的代码级优化）

**做了什么**：`Session` 增加按 SQL 文本的语句缓存（上限 64 条，默认开）。
命中后 `reset()` + 重新绑定即可复用，省掉每次 `prepare`/`finalize`。

**实测（同机、同一轮内、SQLite 内存库、ReleaseFast，`zig build bench`）**：

### 踩坑清单（下次别重复）

1. **`Dal` 按值返回 + 在其中先开会话 = 悬空指针**：`db.lib` 指向 `Dal.lib`，

2. **测试用 `db2`/`m` 不可变时 `deinit` 编译不过**（`*EntityModel` 非 const）。
3. **`{d:0>4}` 在 Zig 0.17 会带出多余符号位**（`2024` → `+2024`）：日期补零一律手写。
4. **内联 `allocPrint(..., .{try quoteAlloc(...)})` 会漏内存**：先取变量再 `defer free`。
5. **查询结果统一归会话 arena**：`children`/`roots`/`descendants`/`pathToRoot` 都返回 arena 切片，

## 2026-11-11（十）MySQL `LOAD DATA LOCAL INFILE` 批量装载：实测快 4 倍

### 用户原话
> 「请继续，先做功能全量迁移，然后再做性能调优」

### 功能：LOCAL INFILE（此前明确列为「不支持」的能力）

**驱动层**（`zzig/src/db/mysql.zig`）：
- 握手时声明 `CLIENT_LOCAL_FILES`（仍按服务端 capability 取交集，服务端不支持就不声明）；
- `Conn.loadDataLocal(sql, data)`：发 `COM_QUERY` → 等服务端 `0xfb` 请求 → **客户端流式发送数据**
  → 空包结束 → 读 OK。数据**不落盘、不需要服务端文件权限**（这是 LOCAL 的含义）。
- 分块：每包 ≤ `max_payload`，结束时单独发一个空包。为此新增 `writeRawPacket`（只发一个包、不自动补终止包）——
  用原来的 `writePacket` 会在「数据正好是 16MB 整数倍」时**提前截断**，这类坑只在超大数据量才暴露。
- 失败**不降级**：没协商上能力 → `error.LocalInfileNotSupported`；服务端 `local_infile=OFF`（MySQL 8 默认）
  → 服务端回 3948，按 `error.Server` 抛且 `lastError()` 带原文。

**表级 API**（`src/dbtable.zig`）：`TableRef.loadDataBatch(session, columns, rows)`
- `columns` 为物理列名、与每行值一一对应；NULL 写成 `\N`；`\\`/`\t`/`\n`/`\r`/`\0` 按 MySQL 默认转义；
- 二进制列（`Value.blob`）**直接报 `error.Unsupported`**（文本装载无法安全表达任意字节，绝不静默截断）；
- 非 MySQL 方言返回 `error.Unsupported`，调用方回落 `insertBatch`（不假装支持）。

**验证**：
- 回环假服务端：断言客户端**声明了** `CLIENT_LOCAL_FILES`、`0xfb` 之后按序收到数据包、内容与期望逐字节一致、空包结束。
- 真库（本机 3307 / MySQL 8.0.29）：5000 行装载 → 影响行数 5000 → `count` 5000；
  其中一行含 **Tab / 换行 / 反斜杠 / 中文**，读回来逐字节一致；另一行 `Amount` 为 NULL，读回来仍是 NULL（不是空串）。

### 性能：同机同轮对比（`zig build bench-mysql`，20000 行 × 5 列）

| 方式 | 第 1 次 | 第 2 次 | 每行 |
|---|---|---|---|
| `insertBatch`（多行 INSERT，5000 行/批） | 897.45 ms / 22,285 行/秒 | 732.73 ms / 27,295 行/秒 | 44.87 / 36.64 µs |
| `loadDataBatch`（LOCAL INFILE） | **224.27 ms / 89,178 行/秒** | **194.02 ms / 103,081 行/秒** | **11.21 / 9.70 µs** |

**结论：约 3.8~4.0 倍**（每行 36~45 µs → 9.7~11.2 µs），两次取样一致，不是抖动。

**为什么差这么多**（不是玄学）：多行 INSERT 让服务端**逐行做 SQL 语法分析 + 表达式求值 + 参数绑定**，
20000 行就是 20000 次解析；`LOCAL INFILE` 走的是**行式解析器**（按分隔符切列），几乎没有语法开销。
批量越大差距越明显——这正是 C# 侧 `DH.MySql` 也支持 `MySqlBulkLoader` 的原因。

**用法建议**（写进 README）：
- 万行以上的日志/采集/导入：`loadDataBatch`；
- 百行级或需要逐行自增 ID：`insertBatch` / `saveBatch`；
- `loadDataBatch` 不返回每行自增 ID（LOAD DATA 语义如此）。

### 踩坑

1. **假服务端必须声明 `CLIENT_LOCAL_FILES`**：客户端按「服务端 capability ∩ 客户端期望」取交集，
   服务端不声明就会被裁掉；表现是握手后立刻断（客户端等下一条包，服务端已退出）。
2. **`writePacket` 的自动补空包会截断 LOCAL INFILE 数据**（见上）→ 单独实现 `writeRawPacket`。
3. 编辑工具的一次「删空行」把 `/// 文档注释` 与 `pub fn ...` 挤到同一行，导致函数体被解析成结构体字段
   （报 `declarations are not allowed between container fields`）。改源码时**别用正则式整段替换**，
   落盘后跑一次 `zig build` 立刻能发现。

## 2026-11-11（十一）MySQL TLS：补齐 `SslMode` 五档（含 std 不支持 `CertificateRequest` 的处理）

### 用户原话
> 「请继续，先做功能全量迁移，然后再做性能调优」

上一轮收尾时我列了剩余四项并建议先做「预处理语句复用」（性能项），用户重申**先功能后性能** →
本轮取「MySQL TLS」这项硬功能缺口：此前的驱动**根本不发 `CLIENT_SSL`**，
连 `require_secure_transport=ON` 的库都连不上，属于「有功能缺口」而不是「性能不够」。

### 做了什么

**驱动层（`zzig/src/db/mysql.zig`）**
- 新增 `SslMode`：`disabled | preferred | required | verify_ca | verify_full`（与 MySqlConnector 同口径，
  `None` 等价 `Disabled`；取值认不出由上层报 `error.InvalidSslMode`，**绝不静默按缺省走**）。
- 握手按协议插入 `SSLRequest`（32 字节：能力位 + 最大包长 + 字符集 + 23 个 0，序号与握手连续），
  随后在**同一条 TCP** 上升级为 TLS，再在 TLS 上发正式的 `HandshakeResponse41`。
- 缺省 `SslMode=Preferred`：服务端支持就加密；TLS 握手失败则**整条连接回退明文重连一次**，
  并把第一次的失败原因打到 stderr（不静默降级）。
- 收发层抽象出 TLS 分支：写侧「TLS 加密 → socket Writer」两级 flush（一个 MySQL 包 = 4 字节头 + 载荷
  两次 `writeAll`，中途 flush 会多一个 TLS record）；读侧走 TLS Reader。
- 读侧**必须循环**：TLS 层返回 0 字节不等于对端关闭 —— 可能只是消费了 `NewSessionTicket` / `KeyUpdate`
  这类控制记录；只有 `EndOfStream` 或 `close_notify` 才算关闭（见下「踩坑 4」）。
- `TlsState` **堆分配**：`std.crypto.tls.Client` 内部持有 Reader/Writer 指针，而 `Conn` 是按值返回的，
  栈上地址会随复制失效。

**连接串（`src/dal.zig`）**：认 `SslMode` / `SSL Mode`、`SslCa` / `CertificateFile` / `SslCert`；
根证书支持绝对路径与相对当前目录两种；`verify_ca`/`verify_full` 未给 `SslCa` 时用系统根证书
（Windows 证书库 / Linux 常见 CA 目录），空证书束直接报错。

### 关键决策：供应商化一份 TLS 客户端（`zzig/src/db/tls_client.zig`）

**为什么**：MySQL 8 只要服务端配了 `ssl_ca`（`--initialize` 自动生成证书的**默认**形态就是如此），
TLS 1.3 握手会发 `CertificateRequest(0x0d)`。std 的 TLS 客户端对该消息走 `else => error.TlsUnexpectedMessage`，
于是**连默认 MySQL 8 的 TLS 都连不上**（不是「部分场景不可用」，而是「几乎全部 MySQL 8 不可用」）。

**怎么做的**：把 std 的 `Client.zig` 复制进 zzig，只加三处（其余逐字未改，便于日后 diff）：
1. `.certificate_request` 分支：计 transcript、置 `cert_requested`（TLS 1.2 的该消息格式不同 → 明确报错，不猜）；
2. 客户端飞行里补一条**空的** Certificate（TLS 1.3 §4.4.2 允许空列表），
   并用 client handshake key 的正确序号加密（首条 = 0，Finished = 1）；
3. 该空消息按协议顺序计入 transcript，客户端 Finished 的校验值才对。

**边界**：不支持客户端证书（双向 TLS 的 mTLS 场景仍未做），但「服务端要求出示证书」时回空列表即可通过
（MySQL 用 `SSL_VERIFY_PEER`，只有 `REQUIRE X509` 才会强制）。**std 支持后应整个文件删掉**。

### 踩坑（都有实测证据，不是猜）

1. **`SSLRequest` 之后服务端会「静默 10 秒」再回 `ER_HANDSHAKE_ERROR(1043) Bad handshake`**：
   用探针逐条打印等待时长，5 个变体全部 **10 000~10 015 ms** → 那是握手超时，
   说明服务端**已经进入 TLS** 在等 ClientHello，而不是「拒绝了 SSLRequest」。
   一开始把 26 字节的错误包当成「服务端拒绝」，方向错了。
2. **协议形态是裸 TLS，不是「TLS 装在 MySQL 包里」**：先用 Python 的 `ssl.wrap_socket` 直连验证；
   再用 TCP 代理抓 `mysql.exe --ssl-mode=REQUIRED` 的真实字节，确认 `SSLRequest` 之后紧跟 `16 03 01 ...`。
3. **std 报 `TlsUnexpectedMessage` 但不告诉你在哪**：把 std 的 `Client.zig` 复制到本地并给每个
   `return error.TlsUnexpectedMessage` 打点，才定位到「未处理的握手类型 0x0d」。
   注意 `else => return error.X,`（逗号）这种写法用「按分号替换」是抓不到的，得单独处理。
4. **TLS 读返回 0 不等于 EOF**：`NewSessionTicket` 会被 TLS 层消费掉而不产生应用数据，
   此时 `readVec` 返回 0；按「0 = 对端关闭」处理会得到假的 `ConnectionClosed`。
   现在改成循环读，只有 `EndOfStream` / `close_notify` 才算关闭（修好后 `Ssl_cipher` 立刻有值）。
5. **`finalResult()` 是破坏性操作**：它内部会写 padding、改哈希状态。想「先取一份 hash 再用」
   必须用 `peek()`（内部复制一份再 final）；用 `finalResult` 取快照会让后续 transcript 全错 →
   服务端回 `decrypt_error`。
6. **进 transcript 的是握手消息本身**，不含 TLS 1.3 记录尾部那个「内层内容类型」字节；
   把它算进去同样会 `decrypt_error`。
7. **证书链坑**：MySQL 自动生成的 server 证书 CN 是本机生成的随机名，`VerifyFull` 连 `127.0.0.1`
   必然 `CertificateHostMismatch`；自签 CA 场景正确档位是 `VerifyCA`（校链不校主机名）。

### 验证（真库，MySQL 8.0.29 @ 3307）

```
[mysql-tls] Required cipher = "TLS_AES_128_GCM_SHA256"
[mysql-tls] None cipher = ""                                  ← 明文档确实是明文
[mysql-tls] VerifyCA（无 CA）按预期失败：TlsCertificateNotVerified   ← 不校验证书就必须连不上
[mysql-tls] VerifyCA(ca) cipher = "TLS_AES_128_GCM_SHA256"
[mysql-tls] VerifyFull 按预期失败（主机名不匹配）：CertificateHostMismatch
```

- `zig build test`：**110/110**（单元 74 + 集成 36）；真库 `-Dmysql-conn -Dmysql-ca` → **36/36**，无泄漏。
- zzig：**70/70**（含 PG 回环、LOCAL INFILE、TLS）。
- `tools/regression.ps1`：**PASSED**。

## 2026-11-11（十二）MySQL 压缩协议（`CLIENT_COMPRESS`）：TLS/压缩两个传输缺口都补齐

### 用户原话
> 「请继续，先做功能全量迁移，然后再做性能调优」

上一轮把 TLS 做完后，「MySQL TLS/压缩」只剩压缩这一半；本轮收掉它，MySQL 驱动的传输层能力就完整了。

### 做了什么

**驱动层（`zzig/src/db/mysql.zig`）**
- 握手按 `opts.compress` 声明 `CLIENT_COMPRESS`；**认证 OK 之后**才切到压缩（协议规定，OK 本身不压）。
- 压缩帧格式：`{3 字节压缩后长度, 1 字节压缩序号, 3 字节解压后长度}` + 数据；解压后长度写 0 表示本帧未压缩。
- 两条独立计数器：内层包序号 `seq`、压缩帧序号 `compress_seq`；每发一条新命令两者都归零（与协议一致），
  读响应时都从对端包头取值再 +1（读写共用一个序列）。
- **写侧**：内层 4 字节头 + 载荷先攒进 `wbuf`，一次 flush 时按 ≤16MB 切帧压缩；
  小于 50 字节的帧、以及压完反而更大的帧，按未压缩形态发（否则小包越压越大）。
- **读侧**：压缩帧解压进 `rbuf`，再按内层 4 字节头切包；已消费部分及时前移避免缓冲膨胀。
- 未压缩路径**完全不变**（缺省关闭），走的是原来那套 `writePacket`/`readPacket`。

**连接串（`src/dal.zig`）**：认 `Compression` / `Compress` / `UseCompression`（`parseBool`，认 `true/1/yes`）。
服务端没声明 `CLIENT_COMPRESS` 时**打印一行说明**并继续未压缩运行 —— 不静默假装压缩了。

### 踩坑

1. **`flate.Compress.init` 断言输出 Writer 缓冲 > 8 字节**：用空的 `Writer.Allocating` 直接 panic。
   改成 `Allocating.initCapacity(gpa, 4096)`。
2. **`packed` 是 Zig 关键字**：测试里拿它当变量名直接语法错（`expected 'an identifier', found 'packed'`）。
3. **测试载荷不能按字节切 UTF-8**：按 `i % 18` 切「多字节内容-test」会切出半个汉字，
   MySQL 直接回 `1366 Incorrect string value`（这条错本身也证明了压缩流里的错误包能被正确解析）。
   改成按完整 3 字节汉字填充、余数补 ASCII。

### 为什么先做这一项（以及为什么没继续做功能项）

| 剩余功能项 | 阻塞点（实测） |
|---|---|
| SQL Server（TDS）驱动 | `127.0.0.1:1433` 不可连、`Get-Service MSSQL*` 无实例、`docker` 未安装 → **没有真库**，只能对着自己写的假服务端测，按「不能猜」的规矩不敢声称可用 |

| Oracle（OCI/TNS） | 同上，且更冷门 |

于是转性能阶段（用户原本定的第二步），从**最确定的热点**入手：带参语句每次都在
`COM_STMT_PREPARE` → `COM_STMT_EXECUTE` → `COM_STMT_CLOSE` 三步走，prepared 句柄完全没复用。

### 做了什么

`zzig/src/db/mysql.zig`：`Conn` 增加预处理语句缓存
- 键 = SQL 文本；值 = `{句柄 id, 列数, 参数数, SQL 副本}`。SQL 副本**自己持有**（不借 arena，
  否则下次 `resetResults` 就悬空）。
- 上限默认 32 条，满了按 **FIFO** 淘汰最旧的一条（热点语句很快稳定，LRU 的收益不值得复杂度）。
- `setStmtCacheLimit(0)` 关闭缓存（同一个进程里做 A/B 用）；`stmtCacheStats()` 给命中/未命中原语。
- `deinit` 先 `clearStmtCache()`（逐条发 `COM_STMT_CLOSE`）再 `COM_QUIT`，并把缓存链表自身的
  缓冲一并释放（**这里踩过**：只清条目不 `deinit` 链表 → 每条连接泄漏 144 字节，真库用例当场抓到）。
- 执行失败**不**清缓存：MySQL 允许错误后继续复用同一句柄（缓存键仍是同一条 SQL）。
- 注意 prepared 句柄是**连接私有**的，所以缓存挂在 `Conn` 上、断线重连自然失效。

### 实测（同一进程内 A/B，`zig build bench-mysql`，3000 次，本机 3307）

| 场景 | 未复用 | 复用 | 提速 |
|---|---|---|---|
| 单参数点查（`WHERE Id = ?`） | 843.48 ms（281.16 µs/行） | 514.38 ms（171.46 µs/行） | **1.64×** |
| 单参数插入（同一事务内） | 932.02 ms（310.67 µs/行） | 574.39 ms（191.46 µs/行） | **1.62×** |

口径说明：
- 两轮在**同一进程、同一连接、同一数据**上顺序跑，先关缓存再开缓存，避免跨轮次相减
  （本机跨轮次绝对值可差 20%+，之前踩过）；
- 插人在一个事务里跑，避免把「每次提交」的 fsync 开销算进协议对比；
- 点查与插人都**热身一次**，把首次 prepare 排除在计时外。

## 2026-11-11（十四）功能迁移续轮：数据库远程服务 `DbService` / `DbClient`（HTTP/1.1 + JSON）

### 用户原话
> 「先不管是否缺，先把功能做迁移，远程服务 DbService这个是能实现的吧」

（同轮更早还问过：「我另外想知道数据库连接是HTTP1.1还是HTTP2.0的？」）

### 先回答 HTTP 版本这个问题（有源码证据，不是印象）
- 本仓 / `zzig` 的客户端走的是 **HTTP/1.1**。之前查过 std 的 HTTP 模块：
  `std/http.zig:13` 里 `Version = enum { @"HTTP/1.0", @"HTTP/1.1" }`，整个 std 里**没有 h2 实现**；
  Rust 侧的参考实现用 `ureq 3.4.2`，同样是 1.1。
- 结论：**数据库连接（MySQL/PostgreSQL/TDS-未做/OCI-未做）是各自的原生二进制协议，不是 HTTP**；
  「HTTP/1.1 还是 2.0」这个问题只对**远程服务那一层**成立，而那一层现在是 1.1。

### 做了什么

1. **`zzig/src/http/server.zig`（新，zzig 提交 `e227114`）**：极简 HTTP/1.1 服务端
   - `Server.init(gpa, io, ctx, handler, .{ .max_body, .max_connections })` + `run(host, port)`（阻塞 accept，每连接一个线程）
   - `RequestView{method,target,path,query,body}` / `Reply{status,body,content_type}`
   - `serveOne`：`Content-Length` 超上限**在读 body 前**就回 413；handler 出错回 500 并打日志
   - 端到端实测：子线程起服务 + 主线程当客户端，收到 113 字节响应（当时 zzig 模块测试 47 项全过）

2. **`Pek.ZCode/src/dbservice.zig`**：把本进程的 `Dal` 暴露成 HTTP 路由
   - `Db/Login` / `Db/Query` / `Db/Execute` / `Db/InsertAndGetIdentity` / `Db/QueryCount` /
     `Db/GetTables` / `Db/Begin` / `Db/Commit` / `Db/Rollback`
   - 统一信封 `{code, data, msg}`（`code=0` 成功），令牌从 JSON `token` 字段或 `?token=` 取
   - 参数是**键值字典**，服务端**按键名字母序**绑定（与 Rust 版口径一致，不依赖调用方顺序）
   - 事务：`Db/Begin` 取一条独立会话并 `BEGIN`，之后带 `tx` 的语句路由回该会话；空闲超时（默认 60 s）
     自动回滚回收；清扫**惰性**做（≤1 次/秒），不额外起定时器

3. **`Pek.ZCode/src/dbclient.zig`**：客户端
   - `login / query / queryTx / execute / executeTx / insertAndGetIdentity / beginTx / commitTx / rollbackTx`
   - `code=401` → `error.Unauthorized`，**404 → `error.Unsupported`**（服务端没这条路由时客户端据此降级），
     其余非 0 → `error.Server`，服务端 `msg` 落在 `lastError()`

### 踩到的四个坑（都实测，不是推测）

1. **`Session` 不能按值搬动**：`Session.stmt_cache` 里的 `Stmt` 指回 `session.driver.sqlite`。
   `beginTx` 里先把 `var s = try openSession()` 再 `slot.* = .{ .session = s }` →
   栈上临时变量出作用域后指针悬空，`rollback` 回收会话时 `sqlite3_finalize` **段错误（地址 0x40）**。
   修法：事务会话一律 `gpa.create(Session)` 后再往里放，之后不再搬；`TxSlot.session` 改成 `*Session`。
2. **事务里的语句必须带 `tx`**：最初 `Db/Execute` 不看 `tx`，于是「BEGIN 之后的 INSERT」落在**新会话**，
   回滚自然不生效（用例的期望值当时是对的，是我实现漏了）。补 `acquire()`：带 `tx` 复用事务会话，
   不带才新开；客户端补 `queryTx` / `executeTx`。
3. **`login` 发的是字面量 `"null"`**：服务端解析 JSON 拿不到 `token` → 必然 401。
   改成发完整请求体（`{db,token}`）。
4. **关监听不能直接 `deinit`**：服务端线程阻塞在 `accept` 时关监听，std 走 `.CANCELLED => unreachable`
   直接 panic。正确收尾：先 `stop=true`，再**自连接一次**把 accept 唤醒，`join` 之后才 `deinit`。

### 与 C# 的已知差异（不静默降级，已写进 `docs/移植对照-NCode.md`）
C# `DbController.Query` 的应答是 **`DbTable` v3 二进制**（`rs.ToPacket()`），本实现返回 **JSON 行列**。
所以「C# 客户端 ↔ Zig 服务端」调 `Db/Query` **不互通**，其余路由是 JSON 信封可以互通。
要二进制互通得再补 `DbTable` v3 编解码（本轮没做）。

### 实测踩到的坑（都是真跑出来的，不是推测）

1. **`MODIFY COLUMN` / `ALTER COLUMN` 是「整列定义替换」**：只写类型会**把 NOT NULL 悄悄去掉**
   （MySQL 8.0.29 真库实测：改完后 `is_nullable` 从 NO 变 YES）。现在语句里必须带 `NOT NULL`/`NULL`
   （MySQL/Oracle 还要带 `DEFAULT`、`COMMENT`），并加了真库断言守住。
2. **PLP 不能按「总长」直接 take**：线上是 `总长(8) + [块长(4)+块]* + 0(4)`，直接取 total 字节会把块长当正文，
   整条令牌流从此错位（表现为后面某个 INTN 长度不是 1/2/4/8 → `error.Protocol`）。
3. **DATETIME2 的值是「时间 5 字节在前、日期 3 字节在后」**；假服务端写成「日期在前」时，客户端仍能读出 8 字节，
   但解码结果变成 2024-02-02（月份断言先炸才发现）。
4. **DECIMALN 的长度字节含符号位**：`符号(1) + magnitude(N)` → 长度要写 `1+N`。
5. **SQLite 重建时索引名是库内全局唯一**：旧表还在就建同名索引会直接报
   `index ix_xxx already exists` → 顺序必须是「建表 → 搬数据 → 删旧表 → 建索引」。
6. **`[_]u8{0} ** N` 在 0.17.1 直接编译报错**（解析成两个 `*`）；`std.posix.getenv` 也已不存在。
7. **`accept` 阻塞时不能直接 `deinit` 监听**（std `.CANCELLED => unreachable` panic）——dbservice 那轮的坑，
   这次在 TDS 回环用例里又差点踩到，已改成「自连一次唤醒 → join → deinit」。
8. **用 PowerShell 改源码会把中文写坏**（`Get-Content -Raw` 按 ANSI 读 UTF-8 → 回写即乱码）：
   本次真踩到一个新建的测试文件（已整文件重写）。纪律再确认：**源码/文档只用编辑工具改**。

### 实测出来的三个反直觉点（都不在文档里，只能靠跑）

- **浮点是大端**：`Binary.IsLittleEndian` 默认 `false` → `Write(Double)` 走 `WriteDoubleBigEndian`
  （1.5 → `3F F8 00 00 00 00 00 00`）。按“小端”猜会全错。
- **整型一律 7bit 变长**，包括 `Decimal.GetBits()` 的四个 32 位分量、`DateTime.ToBinary()`；
  而**行数是 4 字节小端**（`Total.GetBytes()` 原样写，不走 `Write`）。
- **C# 写 null 会抛异常**：`BinaryGeneral.Write(value, type)` 对值类型列执行 `(Int64)(value ?? 0)`，
  而 `value ?? 0` 是装箱的 **Int32** 0 → 拆箱成 Int64 直接 `InvalidCastException`。
  它自己读库时又把 `DBNull` 换成类型默认值 → 本实现与之一致：NULL 写成默认值。

### 做了什么

- **`src/dbtable_packet.zig`（新）**：`encodeAlloc` / `encodeRowsAlloc` / `decodeAlloc`
  + `inferColumnType`（按每列第一个非 NULL 值定类型；全 NULL → string；`Decimal` 超出 96 位尾数/28 位小数
  自动降级为 string，避免溢出）。
- **`Db/Query?format=packet`（也认 `v3`/`binary`）**：返回裸二进制 + `Content-Type: application/x-db-table; version=3`；
  **默认仍是 JSON**（不改旧行为）。错误路径仍回 JSON 信封，客户端据此报错。
- **`DbClient.queryPacket`**：请求 packet 并解码；解失败时把响应开头 200 字节打进 `lastError`。
- zzig 侧补 `DateTime.daysSinceUnixEpoch()` / `toUnixSeconds()`（.NET ticks 换算需要，与 `fromUnixSeconds` 互逆，带单测）。

### 验证（实测输出）

- `src/dbtable_packet.zig` 单测 **5 项全过**：8 列 168 字节与 C# 输出**逐字节相同**（含中文、负数、decimal、
  datetime、byte[]、空串），11 种单列 TypeCode 探测逐字节相同，黄金字节可解回原值，
  NULL 按默认值落字节，坏魔数/未知 TypeCode 明确报错。

## 2026-11-12（二十四）小语种方言覆盖复查：加 `zig build audit-dialects` 审计，修 2 处静默错误

### 用户原话

### 为什么不能凭印象回答

## 2026-11-12（二十八）多表事务与跨库事务守卫

### 用户原话

> 「多表事务的功能做了没有的，另外有一个问题就是如果不小心写了跨库的多表事务这种会告警提示还是会自动分库处理？」

### 结论（先说口径）

- **同库多表事务：支持**。一个会话（= 一个连接）里对多张表增删改，`commit` / `rollback` 一起生效。
- **跨库多表事务：不支持，也不会"自动分库处理"**。本轮新增**显式守卫**：直接报
  `error.CrossDatabaseTransaction` 并打印两张表各自的连接名。理由：
  1. 静默拆成两个独立事务 = 一半成功一半失败，最难排查；
  2. "自动分库"在事务语境下等于分布式事务（需要两阶段提交/协调者），本库没有，也不该偷偷做；
  3. 真要跨库一致，走业务补偿（Outbox / saga），这一点写进诊断文案。

### 新增 API（`src/dal.zig`）

| API | 作用 |
|---|---|
| `connectionOfTables(tables) ![]const u8` | 校验一组表是否同库；跨库→ `error.CrossDatabaseTransaction` + 诊断 |
| `beginTransactionForTables(&s, tables) !void` | 校验同库后在**已有会话**上开事务（同库多表） |
| `execIn(&s, sql, params) !usize` | 在**已有会话**上直执行 SQL（方言改写 + 绑定）——事务内必须用它 |

### 一个关键坑（已写进注释与文档）

`exec` / `execOnTable` 会**新开会话**，在事务里调它们等于另开一个事务，写进去的数据不随调用方回滚。
事务内一律用 `execIn`。另外 `Session` 内含 `ArenaAllocator`，**不能按值返回**给调用方
（两个副本共享同一份缓冲链，`deinit` 必崩，实测 segfault）——所以事务入口只接受 `*Session`。

### 验证

- 真 SQLite 用例：同库 A/B 两表提交后各 1 行；回滚后仍各 1 行（没多出来）。
- 跨库用例：`connectionOfTables(&.{ "A", "L" })` 与 `beginTransactionForTables` 都返回
  `error.CrossDatabaseTransaction`（`L` 表级 `ConnName="Log"`）。
- `zig build unit` 176 项、`zig build integration` **64 passed / 2 skipped / 0 failed**；
  `tools/regression.ps1` → **PASSED**（`report-20261112-231400`）。

## 2026-11-12（二十九）SQL 输出开关接线 + UserStore 真实 ORM 实现

### 用户原话

> 「当前是否有配置文件中有开关是否输出sql的？」

### 结论：**有开关字段，但之前是「假开关」**

| 位置 | 字段 | 之前的状态 |
|---|---|---|
| `src/setting.zig`（`Config/XCode.config`） | `ShowSQL` / `SQLPath` / `TraceSQLTime` / `SQLMaxLength` | 只解析、只序列化，**没有任何执行路径读它** |
| 连接串 | `ShowSQL=True` | 只解析进 `ConnectionOptions.show_sql`，没有消费方 |
| 会话 | — | 没有开关；`session.zig` 只在**失败时**打印 SQL（带错误原因） |

也就是说：配置里写 `ShowSQL=false/true` 对「是否输出 SQL」毫无影响。本轮把它接上。

### 实现（对齐 C# `DbSession.ShowSQL` / `GetSql` / `WriteSQL`）

- `Session.show_sql: ?bool`：`null` = 跟随全局 `Setting.show_sql`；`Dal.openSession` 用连接串 `ShowSQL` 初始化。
- 会话级覆盖：`setShowSql(v)` / `followGlobalShowSql()` / `showSqlScoped(v)` + `restoreShowSql(sc)`（对应 C# `SetShowSql` 返回 `IDisposable` 的作用域还原）。
- 长度与慢 SQL：`Session.sql_max_length` / `Session.trace_sql_time`（0 = 跟随全局；`trace_sql_time = 0` 表示不跟踪）。
- `Session.conn_name`：日志前缀 `[Membership]`，由 `Dal` 开会话时填（主连接用模型 `ConnName`，附加连接用挂载名）。
- `session.setSqlSink(...)`：把拼好的 SQL 文本交给应用层（写文件 / 上报 / 面板 SQL 列表），**`SQLPath` 由应用层实现**——本库不自己造文件日志（轮转/目录策略各项目已有）。
- 输出格式：`[连接名] SQL [0=值, 1=值]`；超长截断（INSERT 前后各留一半，其余截尾部，C# `GetSql` 同口径）；慢 SQL 追加 `  (N ms)`，**即使 `ShowSQL=false` 也输出**。
- **关闭时零开销**：`sqlTimingNeeded()` 为假时连时间戳都不取（`execute` / `queryRows` 直接走内层）。
- 默认值改成 `Setting.show_sql = false`：C# 的 `ShowSQL` 字段默认 true，但 `DbSession.ShowSQL` 的真实默认值取自 `XCode.Debug`（`#if DEBUG`，发布版 false）；本仓没有 DEBUG/RELEASE 之分，直接落地「默认关、配置显式开」，避免默认把每条 SQL 写进日志（刷屏 + IO）。

### 顺带修掉的真实缺陷（接上 ORM 才暴露）

`loginCore` 在「库密码为空 → 任意密码可登并写回散列」与「旧格式自动升级」两个分支里，只写了 `user.Password = ...`，**没有走 setter**。
脏位图不含 `Password`，接上真实 ORM 后 `entity.update` 只写脏列 → **新散列根本不会落库**，该用户每次登录都走「库密码为空」分支。

| `OrmStore.findForLoginAlloc(a, account)` | C# `User.FindForLogin` 顺序：`Name` → 含 `@` 时 `Mail` → 纯数字且 >0 时 `Mobile` → `Code` |

## 2026-11-13（三十一）脏数据驱动：未改不写 / 合并往返 / 分片批量 / 缓存与数据库特性盘点

### 用户原话（连续追加，逐条对上）

> 「还有脏数据的处理」

> 「还有每个实体我记得不是有扩展虚拟字段的，这个功能是不是也迁移了」

### 1. 「未改不写」的根：setter 值相等不置脏（对齐 Pek.RCode `dirty::DirtyState`）

- Rust `Pek.RCode` 生成的 setter 是：`if self.field == value { return; } self.field = value; dirty.mark(...)`。
  本仓原来**无条件置脏** → 赋了相同值也会进 SQL。
- 已改 `codegen.zig` 的 setter 模板：`if (zcode.entity.valueEql(self."X", v)) return;`，
  `valueEql` 对 `[]const u8` 比**内容**（切片直接 `==` 只比 ptr+len），其它走 `std.meta.eql`。
- **副作用必须一起修**：原代码里「先赋字段再调 setter」的写法（`user.Password = x; user.setPassword(x);`）
  现在会因为值相等而**不置脏** → 密码永不落库。已改成只调 setter（`provider.zig` 三处）。
- 重新生成 9 个 membership 实体（`zcodegen --import ../../root.zig`），diff 只有 setter 多一行。

### 2. 批量写：未改的列不进 SQL + 同组一条语句（减少往返）

`entity.saveBatchWith` 现在：
1. **新增** → 全列合并成一条多行 `INSERT`（`upsert` 走方言 `ON CONFLICT` / `ON DUPLICATE KEY`）；
2. **已存在** → 按「脏列签名」分组，**同组一条多行 `UPDATE`**；不同签名各自一条；
3. **没脏列** → 一条 SQL 都不发（计入 `unchanged`）；
4. **不再用整行 upsert 覆盖已存在行** —— 多业务系统并发写同一张表时，未改的列不会把别人刚写的值盖回去。

新增 `sqlbuild.updateMulti`：
- SQLite：`UPDATE t SET c=v.c FROM (SELECT ? AS pk, ? AS c UNION ALL ...) AS v WHERE t.pk=v.pk`
  （SQLite 的 `UPDATE...FROM` **不接受** `(VALUES ...) AS v(a,b)` 的列名列表，实测 `near "(": syntax error`，改走 UNION ALL）
- PostgreSQL 系 / DuckDB / SQL Server：`UPDATE t SET c=v.c FROM (VALUES (...)) AS v(pk,c) WHERE ...`
- MySQL：`UPDATE t JOIN (SELECT ? AS pk, ... UNION ALL ...) v ON ... SET ...`
- 其它方言：`error.Unsupported` → 逐条（每条仍只写脏列）

### 3. 分表分库：分片边界优先于合并

`saveBatchWith` 检测到该表配了分片策略时走 `saveBatchSharded`：
- **先按「连接 + 物理分片表」分组**（不同库/不同表绝不合并、不共用会话）；
- 组内再按「新增 / 脏列签名」分流，每片一次往返；
- 首次写入自动 `ensureShardTable`；
- 用例：两个分片、3 行只改 `Title` → **恰好 2 条 UPDATE**，且 SQL 里没有 `CreateTime`。

## 2026-11-13（三十二）「批量判存再插入」：一条语句、一次往返

### 用户原话

> 「有一种场景，就是有时候会先查某批数据在数据库中是否存在，如果不存在就写入，存在就跳过这种场景，而且判断的条件字段也是惟一键，但这种先查后写的方式在数据量非常大的情况下很慢，这种有适合的方法么？是否有做迁移。」

### 结论：已有 `insert_ignore`，就是给这个场景准备的；本轮补齐了三处会让它用不了/用错的地方

正确做法是**把「判断」交给数据库**，一条语句完成：

| 方言 | 语句 | 往返 |
|---|---|---|
| SQLite | `INSERT OR IGNORE INTO t (...) VALUES (...),(...)` | 1 次（整批多行） |
| MySQL | `INSERT IGNORE INTO t (...) VALUES (...),(...)` | 1 次 |
| PostgreSQL 系 | `INSERT INTO t (...) VALUES (...) ON CONFLICT DO NOTHING`（**不带冲突目标**） | 1 次 |
| SQL Server / Oracle 等 | `INSERT INTO t (...) SELECT ?, ? WHERE NOT EXISTS (SELECT 1 FROM t WHERE 唯一键 = ?)` | 1 次/行 |

对比「先查后写」：N 行数据要先 `SELECT ... WHERE key IN (...)`（还可能分批）再 `INSERT`，
至少 2 次往返、中间还有竞态窗口（查完到插入之间别人插进来 → 唯一键冲突报错）。
上面第三种形态 `ON CONFLICT DO NOTHING` **不带目标列**，所以它忽略的是**任意唯一约束**
（主键、复合唯一索引都算）——正好覆盖「判断字段是唯一键」这个前提。

用法：

```zig
const inserted = try table.upsertBatch(&s, rows, .insert_ignore);
const skipped = rows.len - inserted; // SQLite/MySQL/PG 的影响行数就是「真正插入的条数」
```

### 本轮修的三处（都会让上面的方案失效）

1. **无主键的表用不了**：`upsertBatch` 原来对 `insert_ignore` 也要求「有主键 / 有冲突目标」，
   直接 `error.NoPrimaryKey`。但 `INSERT OR IGNORE` 根本不需要这两样 —— 已放开，
   `insert_ignore` 不做前置检查。
2. **SQL Server 上语义是错的**：`upsertFallback` 无视 mode，一律「先 UPDATE 未命中再 INSERT」，
   于是 `insert_ignore` 会**把已存在的行改掉**。现改为 `INSERT ... SELECT ... WHERE NOT EXISTS`，
   既跳过不覆盖，也不再是「先查再写」的两段式。
3. **新增 `sqlbuild.insertIfAbsent`**：把 `INSERT ... VALUES (...)` 改写成
   `INSERT ... SELECT ... WHERE NOT EXISTS (...)`，键列重复绑定一次（insert 值 + 判存值）。

### 用例（真 SQLite）

- 先插 `A=甲`，再批量 `insert_ignore` `[A=甲改, B=乙, C=丙]` → 返回 **2**（跳过 1 条），
  总数 3，且 `A` 仍是「甲」（**没有被覆盖**，这是与 upsert 的本质区别）；
- 同一批再跑一次 → 返回 **0**；
- 无主键、只有唯一索引 `Key` 的表：同键第二次插入返回 0、总数仍 1。

### 与已迁移能力的对照

| 场景 | API |
|---|---|
| 存在就跳过（唯一键判存） | `upsertBatch(rows, .insert_ignore)`（本轮验证 + 修 SQL Server 语义） |
| 存在就更新（覆盖指定列） | `upsertBatch(rows, .upsert)` |
| 整行替换 | `upsertBatch(rows, .replace)` |
| 按脏列合并更新（并发安全） | `entity.saveBatchWith(..., .upsert)`（只写脏列） |

## 2026-11-13（三十三）「存在就跳过」的风险评估（并纠正上一轮的错误表述）

### 用户原话

> 「针对这个场景你的这种做法是否会有风险」
> 「不能我说什么就是什么，你是专业的，我的建议不一定是对的。」

### 先认错：上一轮的说法有一处不准确

上一轮我写「`INSERT OR IGNORE` / `INSERT IGNORE` / `ON CONFLICT DO NOTHING` 都是忽略任意唯一约束」——
**这是错的**。实际情况：

| 写法 | 忽略哪些冲突 |
|---|---|
| SQLite `INSERT OR IGNORE` | **任意约束**（唯一、NOT NULL、CHECK、外键）→ 静默跳过 |
| MySQL `INSERT IGNORE` | **任意错误**（唯一、NOT NULL、**数据截断**、非法日期…）→ 降级为 warning 后跳过/截断 |
| PG / SQLite `ON CONFLICT DO NOTHING` | **只有唯一/排他冲突**，其它照常报错 |
| 本仓 `insertIfAbsent`（SQL Server 等） | 只按唯一键判存，其它照常报错 |

已改：**SQLite 从 `INSERT OR IGNORE` 换成 `ON CONFLICT DO NOTHING`**（语义收窄），
并加用例守住「NOT NULL 违反必须报错，不能被忽略成 0 条」。

### 真实风险清单

1. **MySQL 的 `INSERT IGNORE` 是数据风险，不只是「跳过」**
   非严格 `sql_mode` 下，超长字符串会被**截断后插入**、非法日期变成 `0000-00-00`、
   NOT NULL 违反被跳过 —— 调用方只看得到「插入数少了几条」，看不出数据已经被改坏。
   **为什么仍然保留它**：本仓 MySQL 客户端开了 `CLIENT_FOUND_ROWS`，
   若改用 `ON DUPLICATE KEY UPDATE k = k`（唯一键冲突才跳过），"跳过"会被算成 matched
   （返回 1），`insert_ignore` 就**再也统计不出真实插入数**；`INSERT IGNORE` 是唯一
   能准确区分「插入/跳过」的形态。
   → 缓解：代码注释与本文档显式告警；**数据质量敏感的表请用 `.upsert` 或先清洗数据**。

2. **SQL Server 的 `WHERE NOT EXISTS` 有竞态**
   两个会话同时判存通过 → 后一个在插入时抛唯一键冲突。
   唯一键保证「不会重复」，但调用方要把「重复键错误」当成「跳过」处理；
   要彻底避免需要 `WITH (UPDLOCK, HOLDLOCK)`（会加大锁范围，需按业务权衡）。

3. **拿不到「哪条被跳过」**
   `insert_ignore` 只返回插入条数（`skipped = 总数 - 返回值`）。
   需要差集（例如要回写「已存在的 id 列表」）就必须走「分批 `IN` 查询 + 返回差集」，
   这不是性能问题而是接口能力边界。

4. **批量过大 → 长事务 / 锁等待 / 死锁**
   `ON CONFLICT`/唯一索引冲突检测会在索引上加锁。默认 5000 行/批仍偏大，
   建议 1000~2000 行/批、**每批独立提交**，并让上层能重试死锁（`1213` / `40001`）。

### 对用户前提的专业意见（有两处我不同意）

- **「先查后写一定慢」不成立**：判断列有唯一索引时，`SELECT ... WHERE k IN (...)` 是一次
  走索引的批量读，很快。真正的成本是**两次往返 + 查与写之间的竞态窗口**，不是索引查询本身。
- **「大部分数据已存在」时，先查后写反而可能更快**：`ON CONFLICT DO NOTHING` 要为每一行
  做唯一索引冲突检测（写放大 + 加锁），而一次索引读就能拿到「已存在」集合。
  只有当「大部分是新增」时，直接插入才明显占优。
- 还有一个前提必须确认：**判断列在库里真的有 UNIQUE 约束**。如果只是普通索引，
  两条相同数据都能插进去，「跳过」根本不会发生（本仓 `insert_ignore` 不报错、直接插入）。

### 选型建议（按优先级）

| 场景 | 做法 |
|---|---|
| 判断列有唯一约束，**大部分是新增** | `upsertBatch(rows, .insert_ignore)`（SQLite/PG 语义干净；MySQL 注意数据质量） |
| 判断列有唯一约束，**大部分已存在** | 分批 `IN` 查询拿差集，只插差集（往返 2 次/批，但冲突检测成本低） |
| 需要知道「哪些被跳过」 | 同上，差集天然就是结果 |
| 数据质量敏感（MySQL，含长文本/日期/枚举） | 不要用 `INSERT IGNORE`；先清洗或走 `.upsert` |

### 验证

- 新增用例：`insert_ignore` 只忽略唯一冲突，NOT NULL 违反照常报 `error.Sqlite`。
- `zig build unit` 194；`zig build integration` **83 passed / 2 skipped / 0 failed**。

## 2026-11-13（三十四）整表缓存按 MaxCacheCount 拒载 + 修掉一个隐蔽的「写后不失效」

### 用户原话

> 「请继续，那还有其他没有迁移完的么？如果有就继续迁移」

### 本轮补的

**整表缓存的内存保护（`TableMeta.MaxCacheCount`）**——之前只解析、没消费：

- `Cache(T).init` 读模型：`MaxCacheCount <= 0`（含时序列被强制置 0）→ **直接禁用整表缓存**，
  `get` / `all` / `count` 全部改走 SQL；
- 装载后发现行数 > `MaxCacheCount` → **主动放弃缓存**（清空已装载的实体），之后同样走 SQL；
- 语义依据：C# `Meta.Cache` 在 `Meta.Count > MaxCacheCount` 时也不走整表缓存。
- 用例（真 SQLite）：`MaxCacheCount=0` → 读仍正确且 `items` 从未装载；
  `MaxCacheCount=2` 但表里 3 行 → 首访后 `disabled`、`all()` 仍返回 3 行；
  `MaxCacheCount=100` → 正常缓存且写后失效。

### 顺带发现并修掉的真 bug：缓存写后失效在「实体名 ≠ 物理名」时完全不生效

- `Cache(T).ensureRegistered` 注册的是 **`T.meta.table_name`（实体名，如 `Small`）**，
  而 `TableRef` 写操作的 `notifyWrite` 发的是 **物理表名（`BH_Small`）** →
  `invalidateCaches` 永远匹配不上 → **写完之后缓存一直是旧数据**，直到 TTL 到期。
- 之前所有整表缓存用例的表名都恰好相同（如 `Item` → `BH_Item` 的用例只用 `dal.table("Item")` 取句柄、
  断言也走 `dal`，没验证「写后读缓存」），所以这个 bug 一直没暴露。
- 修法两处：
  1. `ensureRegistered` 改用**物理表名**注册；
  2. `Dal.invalidateCaches` 把入参归一化后**实体名与物理名都匹配一次**，
     这样无论哪边用哪种名字都能失效。
- 用例守住：`Small`（`BH_Small`）写一行 → 缓存读到旧值 → `update` → 缓存读到新值。

### 逐条对比（C# `DH.NCode/DH.NCode/Cache/` → 本仓）

| C# | 本仓 | 对齐情况 |
|---|---|---|
| `EntityCache<T>`（`Meta.Cache`，整表） | `cache.Cache(T)` | ✅ 本轮重写 |

**策略侧**（用户真正问的「分级 / 策略 / 自动清 / 手动清」）：

| 策略 | C# 口径 | 本仓口径 |
|---|---|---|

| 过期策略 | `Expire` 默认 10s；过期先返回旧数据并异步刷新，超 2 倍才同步阻塞 | `ttl_seconds`（默认取 `Setting.entity_cache_expire`）；过期后**抢到单飞权**的线程同步刷新，其余返回旧快照（stale-while-revalidate） |
| 写后自动失效 | 事务提交/回滚后 `ClearCache(reason, true)`；批量写也整体失效 | `TableRef` 写通知（带连接名 + 可选主键）→ 整表缓存整体失效；批量/表级写同样整体失效 |
| 单对象缓存写后失效 | `_singleCache?.Remove(e)`（**按主键精确**），批量写才整体清 | 新增 `invalidate_key` 钩子：`entity.update/delete` 带 PK、`TableRef.insert` 带自增 ID → **只丢那一行** |
| 手动清缓存 | `Clear(reason, force)`：`force` → 下次阻塞到新值，否则下次异步 | `invalidate()`（下次读刷新，多线程下可先拿旧值）/ `invalidateForced()`（下次读阻塞到新值） |
| 命中统计 | `Total` / `Success` / `ShowStatics()` | `stats()` → `total/success/loads/over_limit/evicted` + `hitRate()`，原子累加零锁 |
| 作用域隔离 | `ConnName` + `TableName` | `CacheHook{table_name, conn_name}`，`TableRef` 携带 `conn_name`（分库分片取 `ShardModel.conn_name`） |
| 单对象缓存容量 | `MaxEntity` 默认 10000 + 定时清理 | `max_entries` 默认 10000，超出按访问序号**批量淘汰到 90%**（一次扫描 + 排序） |
| 谓词查询走缓存 | `Meta.Cache.Find(e => ...)` / `FindAll` | `Cache.find(pred)` / `Cache.findAll(pred)` |
| 空值缓存 | 「不要缓存空值」 | 同样不缓存空值 |

### 为什么不用后台线程刷新（与 C# 的显式差异）

C# 用 `LazyConsumer` 起线程做异步刷新。本仓改为 **单飞 + 其余线程返回旧快照**：

- 效果等价（过期瞬间只有一个线程付出装载代价，其余请求立刻返回，不会被阻塞）；
- 但**零常驻资源**：不起后台线程、不额外占连接（多表/亿级设备场景下，每表一个刷新线程 + 一条连接是实打实的浪费）；
- `dbcache.LazyConsumer` 仍在，留给真正需要「后台串行消费」的场景（统计、审计落库等）。

### 顺带修掉的两个真 bug

1. **悬垂指针**：旧 `Cache.reload` 直接 `self.items = entity.queryRows(...)`，而 `entity.queryRows` 的字符串指向
   **会话结果集 arena**；同一会话下一次查询会重置它 → 缓存里读到脏数据/野指针。现在每个快照把行
   `cloneEntity` 深拷贝进自己的 arena，用例「会话后续查询不会破坏缓存内容」守住。
2. **快照释放时机**：读路径无锁（原子指针发布），旧快照不能立刻 `free`（读线程可能还拿着它的切片）。
   改为 `retired` 槽**延迟一代**释放——内存代价最多多留一个快照（且被 `max_rows` 封顶）。

## 2026-11-13（三十七）多系统共用同一张表：跨进程版本号 + 恒定成本行数判定

### 用户隐含要求

> 「这个 Sql 就是要考虑支持至少上百万甚至上亿物联网设备高并发以及**多系统共用数据库表**、分库分表等应用场景的。」

上一轮把两级缓存的分级/失效/隔离做完了，但**跨进程**这一环还缺：两个系统写同一张表时，
A 进程写的行，B 进程的本地缓存不知道 → 只能等 TTL 过期（默认 10s）才看得到。

### 本轮补齐

| 能力 | C# | 本仓 |
|---|---|---|
| 跨进程失效通知 | `CacheInvalidator`（`XCode:Cache:Ver:{table}` 版本号 + `ICache` Provider） | `dbcache.CacheInvalidator` **接进 `Dal`**：写操作自动 `bump`，读缓存定时 `poll` 后比对 |
| 读方感知 | `EntityCache.CheckDistributedVersion()`（每次访问查 Provider） | `Cache.checkRemote()` / `SingleCache.checkRemote()`：**默认每 1s** 拉一次远端版本，热路径只读本地版本（零网络开销） |
| 大表行数 | `Session.Count` → `LongCount`（<100w 精确、否则统计，缓存 60s） | `Dal.countUpTo`（恒定成本）+ `Dal.countTotal`（消费 `Setting.full_count_floor`：小表精确、大表统计、无统计则警告后退回精确） |

关键口径：

- **`bump` 不得回调 `Dal.invalidateCaches`**：本地已由 `Dal` 自己失效，否则无限递归。
  为此 `CacheInvalidator` 拆成 `markWritten()`（只广播）与 `invalidate()`（广播 + 本地失效）。
- **热路径不碰网络**：`Dal.remote_cache.local_version()` 只读进程内 map；`poll()` 才访问 Provider，
  且按 `remote_poll_ms`（默认 1000）节流。没挂协调器时只有一次判空（`bench` 数字未变）。
- **`countUpTo` 与表大小无关**：`SELECT COUNT(*) FROM (SELECT 1 FROM t LIMIT n+1)`，
  SQLite/MySQL/PG 用 `LIMIT`、SQL Server 用 `TOP(n)`、Oracle 用 `ROWNUM`——不扫全表、不依赖 ANALYZE。
- **`countTotal` 的顺序**：先 `countUpTo(floor+1)`（≤ floor 即精确且便宜）→ 超 floor 读统计
  （`sqlite_stat1` / `information_schema` / `pg_class` / `sys.partitions` / `USER_TABLES`）→
  拿不到统计就打警告再 `COUNT(*)`（慢是可预期的，日志里提示去 ANALYZE）。

### 顺带修掉：并发首访重复注册（内存泄漏）

加「读路径检查版本」时把 `ensureRegistered` 放进了 `snapshotForRead`，4 个线程首访会**各注册一次**
（`registered` 是普通 bool）→ 测试直接报 `leaked 1 allocations`（`cache_hooks` 容量 3 的缓冲区）。
修法：① 注册只保留一条路径（`reloadInner` 内，已在 `load_mutex` 里）；② `SingleCache` 的注册加
`reg_mutex` 双检；③ `Dal.unregisterCache` 改成**清干净所有匹配项**（swapRemove 后不前进）。

### 验证

- `zig build test` → **293 passed / 2 skipped / 0 failed**（新增 `tests/integration_cache_remote.zig` 5 项：
  跨进程版本过期整表缓存、本进程写入广播版本、单对象缓存跨进程整体失效、`countUpTo`、`countTotal`）。
- `zig build bench` 数字未变（整表缓存命中仍 **0.03 µs**、单对象 **0.08 µs**）——说明未挂协调器时确实零开销。
- 多进程实测方式：单进程内用 `MemoryProvider` 模拟「另一个进程」（`provider.setFn` 递增版本），
  缓存下一次访问即重载；生产换 Redis/NATS 等实现同一接口即可。

## 2026-11-13（三十八）行数判定上真库：抓到一个「SQL 里硬写 `?`」的方言 bug

### 为什么要单独跑真库

`countUpTo` / `countApprox` 全是**方言相关 SQL**，只在 SQLite 上验证等于没验证：

- 占位符：SQLite/MySQL 是 `?`、PostgreSQL 家族是 `$1`、SQL Server 是 `@p0`、Oracle/达梦是 `:1`；
- 行数限制：SQLite/MySQL/PG 用 `LIMIT`、SQL Server 用 `TOP(n)`、Oracle 用 `ROWNUM`；
- 统计表：`sqlite_stat1` / `information_schema.TABLES` / `pg_class` / `sys.partitions` / `USER_TABLES`。

### 抓到的真 bug（已修）

`sqlbuild.countUpTo` 与 `Dal.countApprox` 第一版把占位符**硬写成了 `?`**：

```
SQL: SELECT COUNT(*) FROM (SELECT 1 FROM "zcode_probe" LIMIT ?) zcode_t
原因: PostgreSQL 错误（SQLSTATE 42601）：syntax error at or near ")"
```

本仓的 `sqlbuild` 其余地方都用 `kind.pushPlaceholder()`，只有这两处偷懒写了字面量 `?` →
在 SQLite 上跑得好好的，一到 PG 就崩（`?` 根本不是 PG 的占位符，被当成语法错误）。

修法：
- `pushPlaceholder` 统一生成（`countUpTo` 的 `LIMIT` / `TOP` / `ROWNUM` 都走它）；
- `countApprox` 的 SQL 用 `Buf` + `pushPlaceholder` 拼（`allocPrint` 的格式串必须 comptime 已知，
  运行期模板拼不了——也踩了一次编译错误）。

**教训（写进规矩）：只要 SQL 里出现参数，就必须走 `pushPlaceholder`；字面量 `?` 一律视为 bug。**

### 真库实测（`tools/mysql-local.ps1` + `tools/pg-local.ps1`）

| 能力 | SQLite | MySQL 8.0.29 | PostgreSQL 16 | 结论 |
|---|---|---|---|---|
| `countUpTo(limit)` | 3 / 5 / 0 ✔ | ✔ | ✔ | 三种方言都对（判定用不着扫全表） |
| `countRows`（精确） | 5 ✔ | ✔ | ✔ | — |
| `countTotal`（floor=1000） | 5 ✔ | ✔ | ✔ | 走 countUpTo，小表精确 |
| `countTotal`（floor=1） | 5 ✔ | 5 ✔ | 5 ✔ | **大表分支**：MySQL 读到统计估算 = 5，SQLite/PG 无统计 → 警告后退回精确 |
| 整表缓存超限不装载 | 0 行 ✔ | ✔ | ✔ | `MaxCacheCount=3` 表 5 行 → 一行不留 |
| 删到 3 行后恢复缓存 | ✔ | ✔ | ✔ | 静默期清掉后可正常装载 |

### 新增能力

**1. 行锁 `Query.lock`（多实例并发消费同一张表）**

```zig
var q = zcode.Query.init(gpa);
q.limit = 100;
q.lock = .skip_locked;         // FOR UPDATE SKIP LOCKED
const tasks = try table.queryRows(&s, &q);   // 必须在事务里
```

- MySQL 8.0 / PG 9.5+ / Oracle 11g+ → `FOR UPDATE SKIP LOCKED`（另有 `.update` / `.no_wait`）
- SQL Server → `WITH (UPDLOCK, READPAST)`（**表提示**，位置在表名后，不是句尾后缀）
- SQLite → 显式 `error.Unsupported`（它只有库级写锁，没有行锁）

断言两人拿到的 **id 不相交** —— MySQL 与 PostgreSQL 都通过（SKIP LOCKED 真的生效）。

**2. SQLite 并发档位（连接串可控）**

```
Data Source=app.db;Provider=SQLite;JournalMode=WAL;Synchronous=NORMAL;CacheSize=-64000
```

`JournalMode`（WAL/DELETE/MEMORY/OFF）、`Synchronous`（Off/Normal/Full，也认 0/1/2）、`CacheSize`；
`busy_timeout` 固定 5000ms。任何 PRAGMA 失败**只降级不报错**（网络盘不支持 WAL 的典型情形）。

### 实测：WAL 并没有更快（所以**不做默认值**）

`zig build bench` 新增两项（临时文件库，500 行 × 2 轮取第二轮，单行一事务）：

| 用例 | 单次 | 说明 |
|---|---|---|
| 文件库写（DELETE+FULL，SQLite 原生默认） | **~61 µs/行** | 基准 |
| 文件库写（DELETE+NORMAL） | ~74 µs/行 | — |
| 文件库写（WAL+NORMAL） | ~143 µs/行 | **慢约 2.3×** |

「写中并发读」（一边写 300 行、另一个线程死读）：两种档位都没出现 `SQLITE_BUSY`，
读次数同量级（~3400 次 / 写入窗口）。也就是说在这个工作负载上 WAL **没有收益、只有代价**。

**决策**：`journal_mode` / `synchronous` **默认不设置**（保持 SQLite 原生），由使用方按场景显式选：

- 长写事务（批量导入）同时要求别人持续能读 → `JournalMode=WAL;Synchronous=NORMAL`
- 网络盘（SMB/NFS）→ **绝不开 WAL**（`-shm` 共享内存不可靠）

> 说明：同机不同时刻绝对值会差很多（本轮再测时机器负载高，DELETE 也涨到 ~2700 µs/行），
> 但多轮 WAL:DELETE 始终约 2:1，比例结论稳定；绝对值不可跨轮次相减（既有度量纪律）。

| SQLite | **3.54.1**（2026-10-16） | **3.53.4**（zig 动态加载的 DLL） | UPSERT **3.24**、`UPDATE ... FROM` **3.33**、`RETURNING` + 省略目标 `DO UPDATE` **3.35**、参数上限 32766 **3.32**、`RIGHT/FULL JOIN` **3.39** |
| PostgreSQL | 17.x 线 | **16.2.0**（本机 5433） | `RETURNING` **8.2**、`ON CONFLICT` 9.5、`SKIP LOCKED` 9.5 |

MySQL 官方手册对 `VALUES(col)` 的原话是 **deprecated，且 subject to removal in a future version**
（9.x 手册里仍在，但已明确是「将来会删」）。也就是说**继续用老写法不是「兼容」，而是埋雷**。

### 落地：能力不能是编译期常量，只能「连上之后探一次版本」

- `dialect.ServerVersion`：解析 `8.0.29` / `5.7.44-log` / `10.11.6-MariaDB-…` / `16.2 (Debian …)` / `3.54.1`。
  **先跳过前导非数字**再读，所以带 `SQLite version …` 前缀也认；只有紧邻 `.` 且后面是数字才算下一段
  （否则 `3.54.1 (2026-10-16)` 会把日期读成版本段）。取不到数字返回 `null`，**不猜**。
- `dialect.Features`：目前只有两个「关掉仍然正确」的开关 —— `mysql_row_alias`（8.0.19+，**MariaDB 强制关**）
  与 `pg_returning`（8.2+）。每个开关都必须有回退分支，否则它就该是「最低版本要求」而不是开关。
- `Dal.probeVersionOnce`：整套 Dal **只探一次**（`probe_code` 单 atomic，打包 `flavor|major|minor|patch`），
  SQLite 走 `select sqlite_version()`、MySQL `SELECT VERSION()`、PG `SHOW server_version`；SQL Server **不探**
  （`@@VERSION` 首个数字是发布年份，解析必错，而它也不用这两个能力）。
  探测失败 → 记 `probe_failed` 走保守档 + **告警一次**，不影响连接可用性。
- `Dal.table()` / `tableShardOn()` 把 `features` 注入 `TableRef`（值语义，默认 `conservative`）。
- 运维可观测：`Dal.describeServerAlloc()` → `8.0.29 MySQL（行别名=开 / RETURNING=关）`。

### MySQL upsert 改用行别名

```
INSERT INTO `t` (`Code`,`Qty`) VALUES (?,?) AS zcode_new
  ON DUPLICATE KEY UPDATE `Qty` = zcode_new.`Qty`
```

别名固定 `zcode_new`（MySQL 规定别名不能与表名相同）。5.7 / 8.0.18 / **MariaDB** 自动回退
`Qty = VALUES(Qty)`（用 `table.features = .conservative` 可强制走老写法，测试里就是这么对照的）。

### PostgreSQL 自增回写：`INSERT ... RETURNING`（省一次往返）

PG 驱动**没有** `lastInsertId`（注释里一直写着「需 `RETURNING`，恒为 0」）。现在 PG 系插入带自增列时
直接在 insert 语句尾部追加 `RETURNING "Id"`，**一次往返**拿到 ID；拿不到就报
`error.NoReturningRow`，不再假装成功返回 0。

### 顺带修掉的三个真 bug（都是本轮实测暴露的）

1. **主连接不应用 SQLite PRAGMA**：`openSessionRaw` 早先直接调 `sqlite.Db.open`（不带选项），
   于是连接串里的 `JournalMode` / `Synchronous` / `CacheSize` **只在从库 / 命名连接上生效**，
   主连接反而被忽略（第（三十九）节的档位可配等于白做）。现已统一收敛到 `openSessionWith`
   （全 `null` 时与 `Db.open` 完全等价）。
2. **`upsert` 在「没有可更新列」时生成空子句**：只写主键时 `... DO UPDATE SET` / `ON DUPLICATE KEY
   UPDATE` 后面是空的 → 语法错。现在**明确报错** `error.UpsertNeedsUpdatableColumn` 并给出规避方式。
3. **探测不能借用即将返回的会话**：`Session` 的 SQLite 语句缓存里 `Stmt` 持有 `*Db`，而 `Session` 是
   **按值返回**的（返回时地址会变）。在 `openSessionWith` 里用主会话 prepare 一次再 `return s`，
   缓存就指向失效地址 → `deinit` 时 `finalize` 段错误（本轮实测 18 个用例连环 crash）。
   现在探测**用独立临时会话**，探完即 `deinit`。

### 关于「只写主键的 upsert」——三方言实测结论（别再猜）

| 方言 | 尝试的写法 | 实测结果 |
|---|---|---|
| SQLite 3.49.1 | `ON CONFLICT("Id") DO NOTHING` | ❌ `NOT NULL constraint failed`（**DO NOTHING 不处理 rowid 冲突**，绕开冲突判定直接插入） |
| SQLite 3.49.1 | `ON CONFLICT DO NOTHING`（省略目标） | ❌ 同上 |
| SQLite 3.49.1 | `ON CONFLICT("Id") DO UPDATE SET "Qty"=excluded."Qty"` | ✅ **可用**（DO UPDATE 能命中 rowid 冲突） |
| MySQL 8.0.29 | `... VALUES (?) AS zcode_new ON DUPLICATE KEY UPDATE Id = Id` | ❌ `ERROR 1052 Column 'Id' in field list is ambiguous`（用了行别名后裸列名判为歧义，必须限定目标表） |
| MySQL 8.0.29 | `... AS zcode_new ON DUPLICATE KEY UPDATE Id = \`t\`.\`Id\`` | ❌ `ERROR 1364 Field 'Code' doesn't have a default value`（严格模式**先校验未提供列**，即使本来会走更新分支） |
| PostgreSQL 16.2 | `ON CONFLICT ("Id") DO NOTHING` | ✅ 可用（冲突时不插入 → 不校验列） |

→ 结论：SQLite / MySQL 上「只写主键」的 upsert **无法表达**，统一明确报错而不是发一条注定失败的 SQL。
（MySQL 的「恒等赋值」写法也一并去掉：它过不了严格模式，留着只会误导。）

### 最低版本要求（写进硬约束）

| 方言 | 最低版本 | 原因 |
|---|---|---|
| SQLite | **3.24**（UPSERT）/ **3.33**（`UPDATE ... FROM`，批量脏列更新） | 低于此会在运行期报语法错 |
| MySQL / MariaDB | 5.7（8.0.19 以下自动回退 `VALUES()`） | 行别名需要 8.0.19 |

### 三、本轮的性能项：PostgreSQL 预处理语句复用

**为什么挑它**：MySQL 侧上一轮已经做了同款复用（实测 1.64×），PG 侧每次带参语句都是
`Parse + Describe + Bind + Execute + Sync` **五条消息**，服务端每条都要重新解析 + 规划；
而 ORM 热路径恰恰是「同一条带参 SQL 反复执行」（点查、单行更新）。这是目前最确定的热点。

**做法**（`zzig/src/db/postgres.zig`）：

- 命名预处理语句 `zcode_p{N}` + `std.StringHashMapUnmanaged` 等价物（小数组线性查找，上限 32，足够）；
- 首次：`Parse(name)` + `Describe(statement)` + `Bind` + `Execute` + `Sync`，并把 **`RowDescription` 的列名拷进缓存**；
- 之后：只发 `Bind(portal="", statement=name)` + `Execute` + `Sync`，列名直接复用；
- 淘汰：FIFO，淘汰时向服务端发 `Close(statement)` + `Sync`，避免命名语句在会话里无限累积；
- 每条缓存自带 `ArenaAllocator`（**堆指针**：`ArrayList` 扩容会按字节移动元素，内联 Arena 一旦移动，
  之前取出的 `allocator()` 就悬垂）；
- `setStmtCacheLimit(0)` 关闭（同进程 A/B），`stmtCacheStats()` 给 hits/misses/size。

### 四、顺带修掉的真 bug：PG 错误后连接直接作废

写用例时先复现再修（`tests/integration_pg_driver.zig`）：

```
// 先制造一次服务端错误（表不存在）
queryRows("SELECT * FROM zcode_no_such_table_xyz") → error.Server ✅
// 再正常查询
queryRows("SELECT 1") → ???   ← 修改前：失败（协议错位）
```

根因：`BE_ERROR => return self.failFromError(...)` **直接把错误返回了**，没有把服务端随后必发的
`ReadyForQuery` 读掉 → 残留在缓冲里，下一条语句读到它就错位。修法是错误分支先
`drainUntilReady()` 再返回错误。

**影响面**：连接池里一条连接踩一次错（唯一键冲突、类型错误、超时取消）就会污染后续所有请求 ——
这类问题在生产上极难定位，属于「必须修」而不是「顺手」。

### 五、实测（同进程 A/B，本机 PG 16.2 @5433，3000 次/项）

| 用例 | 不复用 | 复用 | 提速 |
|---|---|---|---|
| 点查（`WHERE "Id" = $1`） | 546.76 ms（182.25 µs/次） | **334.03 ms（111.34 µs/次）** | **1.64×** |
| 单行插入（同事务内） | 508.53 ms（169.51 µs/次） | **334.32 ms（111.44 µs/次）** | **1.52×** |
| 复用阶段命中率 | — | **100.0%**（hits=8998 misses=2，缓存 2 条） | — |

口径：同一进程、同一连接、同一批数据；先关缓存再开缓存；各自热身 1 次；插入放同一事务避免把 fsync 算进去。
与 MySQL 侧（1.64× / 1.62×）几乎一致 —— 两套独立协议得出同一量级，说明**收益来自省掉服务端解析/规划**，
不是实现巧合。基准入口：`zig build bench-pg -Dpg-conn="..."`（不进回归门禁）。

## 2026-11-14（四十五）DuckDB 执行驱动（嵌入式，动态加载 C API）+ 动态库加载下沉

### 一、为什么走「动态加载 C API」

DuckDB 没有网络协议（进程内嵌），只有两条路：链接 C 库，或**动态加载** C 库。
选后者，理由与 SQLite 驱动一致：不链 libc、不把几十 MB 的库塞进产物，
现场把 `duckdb.dll` 放到 exe 同目录即可用，换版本只是换文件。

### 二、动态库加载下沉（`zzig/src/dyn.zig`）

原来这套 `LoadLibrary` / `GetProcAddress` / `FreeLibrary` 的薄封装写在 `sqlite.zig` 里，
DuckDB 也要同一套 → 抽成 `zzig.dyn`（`Module.load/lookup/close` + `exeDirAlloc`）。
注意 **Zig 0.17 的 `std.DynLib` 不支持 Windows**（只有 linux/mac/BSD 分支），所以 Windows 必须自己走 kernel32。

### 三、驱动实现要点（`zzig/src/db/duckdb.zig`）

- **ABI 风险点写进头注释**：`duckdb_result` 是**按值返回**的 C 结构体，
  字段顺序必须与 `duckdb.h` 一致（`deprecated_column_count / deprecated_row_count /
  deprecated_rows_changed / deprecated_columns / deprecated_error_message / internal_data`，
  `idx_t = uint64_t`）；驱动只用函数取值，不直接读字段。
- 缺符号即判失败：`Lib.load` 逐个 `lookup`，任何一个关键符号缺失就关闭模块并换下一个候选路径，
  最后返回 `error.DuckDbNotAvailable`（**打日志说明去哪放 dll，不是 panic**）。
  本机实测：`[zzig.duckdb] 未找到 DuckDB 动态库（尝试过：duckdb.dll）…`，用例断言的就是这个错误。
- 列值还原按 `duckdb_type`：整数族（含 hugeint/varint，超出 i64 保留文本不截断）/ 浮点 / Decimal /
  Date·Time·Timestamp / BLOB（走 `duckdb_value_blob` 后 `duckdb_free`）/ 其余文本。
- 参数走客户端内联（`inline.zig`），与 TDengine / ClickHouse 同口径；
  无自增回写（`lastInsertId` 恒 0，要 ID 用 `RETURNING`）。
- 池化：DuckDB 是嵌入式单进程库 → `supportsPooling` 返回 false（多开会抢文件锁）。

### 四、本仓接线

`session.Driver` 新增 `.duckdb`；`Dal` 新增 `duck_lib`（生命周期与 Dal 一致，`deinit` 时关库）；
`initWithModel` 对 `.duckdb` **先把库找好**（缺库立即报，不拖到第一次查询）；
版本探测走 `SELECT version()`。

## 2026-11-14（四十四）MongoDB 执行驱动（BSON + OP_MSG + SCRAM-SHA-256）

### 一、定位：**文档库**，不是 SQL 库

MongoDB 没有表结构、没有 JOIN、没有 SQL；C# 侧 `Database/MongoDB.cs` 的注释写得很清楚：
「MongoDB 不使用 SQL，大部分 SQL 操作方法会抛出 NotSupportedException，通过 MongoDB.Driver
直接操作集合和文档」。所以这次迁移的是**驱动**（协议 + 文档 API），而不是「把 SQL 翻译成 Mongo 查询」。

- `zzig.db.mongodb`：文档级 API `insert` / `findAlloc` / `update` / `delete` / `count` / `runCommandAlloc`；
- 本仓：`Session.mongodbConn()` 暴露驱动；`Session.execute` / `queryRows` 对 MongoDB 明确
  `error.Unsupported` 并打印「请用 mongodbConn 走文档 API」——**不编造一种看起来能用的语法**。

### 二、BSON 编解码（`zzig/src/db/bson.zig`）

- 支持 `double/string/document/array/binary/ObjectId/bool/UTC datetime/null/regex/int32/timestamp/int64`；
  `Decimal128` 等未解释类型保留在 `raw` 里（**不丢数据**）。
- 解析结果全部复制进调用方 allocator（通常传 arena），源缓冲可立刻释放。
- 数组就是「键为 `"0","1",…` 的文档」，与规范一致。

### 三、线协议与鉴权（`zzig/src/db/mongodb.zig`）

- **OP_MSG(2013)**：`flagBits(u32)` + 段；发送只用 kind 0（单文档），读回逐段找 kind 0，kind 1 按长度跳过。
- 消息头 16 字节；响应 `ok` 必须是 1.0/1（对 `double` 比 1.0，不能用 `!= 0` 判真），
  失败时把 `code` + `errmsg` 收进 `lastError`。
- 握手 `hello`：上报 `client.driver` / `client.application`，并检查 `maxWireVersion >= 6`（OP_MSG 门槛 3.6+）。
- **SCRAM-SHA-256**（4.0+ 默认）：`saslStart` → 服务端 `r/s/i` → PBKDF2-HMAC-SHA256 → `saslContinue` + proof →
  **校验服务端签名 `v=`**（防伪造服务端）。服务端只给 SCRAM-SHA-1 时明确报 `error.UnsupportedMechanism`，
  **不静默降级到弱机制**。

## 2026-11-14（四十三）ClickHouse 执行驱动（HTTP 8123）+ 参数内联下沉为公共件

### 一、为什么是「HTTP 接口」而不是 native 协议

ClickHouse 官方对外提供两条通道：native TCP（9000，自有二进制协议 + 压缩块）与 **HTTP（8123）**。
C# 侧 `XCode.ClickHouse` 也是走 HTTP。选 HTTP 的理由：

- native 协议要自己实现块压缩/校验与查询状态机，体量≈再造一个 TDS，而收益只是省掉 HTTP 头；
- HTTP 通道有 `default_format=JSONCompact`，一次请求直接拿「列名 + 列类型 + 行」的结构化结果；
- 与刚做完的 TDengine REST / InfluxDB 共用同一套 HTTP 客户端与回环测试范式。

### 二、实现（`zzig/src/db/clickhouse.zig`）

- 请求：`POST {base}/?database=<db>&default_format=JSONCompact`，body 是纯文本 SQL；
  鉴权用 `X-ClickHouse-User` / `X-ClickHouse-Key` **头**（口令不进 URL，避免落到反代日志）。
- **为什么不按「是不是 SELECT」去拼 `FORMAT xxx`**：拼错就是 DDL 语法错。
  `default_format` 是 URL 级默认值，对 `INSERT`/`DDL` 无影响，对查询自动生效 —— 一条路走通两种语句。
- 响应：`{"meta":[{"name","type"}],"data":[[...]],"rows":n}`；非 2xx 的 body 是
  `Code: 62. DB::Exception: ...` 文本 → 收进 `lastError` 并返回 `error.HttpFailed`；
  代理层的 `{"exception": "..."}` 也认。
- **类型还原按 `meta[].type`**（这一步不做就会拿到一堆文本）：
  - `Nullable(T)` / `LowCardinality(T)` / `SimpleAggregateFunction(f, T)` 外壳剥离（可嵌套）；
  - **64 位整数默认被引号包起来**（`output_format_json_quote_64bit_integers=1`）→ `Int64/UInt64` 的 `"123"` 必须解析回整数；
  - `Int*`/`Float*`/`Decimal*`/`Date*`/`DateTime*` 分别还原；`Array/Tuple/Map` 原样序列化成 JSON 文本（业务侧自己解析）。
- `exec` 恒返回 0：ClickHouse 把「写入行数」放在 `X-ClickHouse-Summary` **响应头**，本驱动只读响应体
  （已在注释里写明，别把这个 0 当「没写进去」）。
- `ping()` → `GET /ping`；`serverVersionAlloc()` → `SELECT version()`；无自增、无事务（上层明确 `error.Unsupported`）。

### 三、参数内联下沉（复用纪律）

（对外 API 不变，原有单测继续守着它）。扫描规则不变：跳过 `'...'`（含 `''`）、`"..."`、`` `...` ``、`--`、`/* */`。

> 踩坑记录：模块名不能叫 `inline`（Zig 关键字），别名用 `sql_inline`。

### 四、验证（无实例）

- `zzig/src/db/http_loopback_test.zig` 新增 2 例：① 断言方法/路径/查询串（`database=`、`default_format=JSONCompact`）/

- 单测：JSONCompact 类型还原（含 64 位整数按字符串回、`Nullable`/`LowCardinality` 外壳、`DateTime`、`Array` 文本化）、

## 2026-11-14（四十七）ODBC 执行驱动：一家盖 7 个方言，21 个方言全部有执行层

### 一、为什么要做这一家

上一轮把 Oracle 收掉后，`hana` / `firebird` / `db2` / `dameng`（达梦）/ `iris` / `access` / `sqlce`
这 7 个方言**仍然只有 SQL 生成层**（`dialect.zig` 全部就绪，但没有执行驱动）。
它们在 C# 侧（`DH.NCode.{Hana,Firebird,DB2,DaMeng,IRIS,Access,SqlCe}`）**本来就走 OLE DB / ODBC 桥**，
没有值得自实现的自有线上协议 —— 所以**一个 ODBC 驱动 = 7 个方言**，是剩余欠账里性价比最高的一块。

### 二、实现（下沉 `zzig.db.odbc`）

- `Lib.load` 动态加载 `odbc32.dll`（Windows 系统自带）/ `libodbc.so`（unixODBC），只绑 16 个入口；
  字符串类入口按 **W 变体 → 裸名** 顺序找（Windows 的 odbc32 只有 `SQLDriverConnectW/A`，unixODBC 是裸名）。
- **一律走 W 变体**（`SQLDriverConnectW` / `SQLExecDirectW` / `SQLDescribeColW` / `SQLGetDiagRecW` + `SQL_C_WCHAR`）：
  A 变体按系统 ANSI 代码页（本机 936）解码，中文列值/表名会随机器变形；进出各做一次 UTF-8 ↔ UTF-16LE 转换。
- 取值口径与 Oracle/DuckDB 一致：**所有列按文本取**，由 ORM 按模型列类型转换；缓冲区按
  `SQLDescribeCol` 的 `ColumnSize` 夹在 `[64, 32767]` 字符，**被截断时打日志**（不静默，CLOB 请用 `SUBSTR` 分段）。
- 参数不走 `SQLBindParameter`，用客户端内联（`zzig.db.inline`）。
- **事务**：ODBC 默认 autocommit ON。我们按 ORM 语义处理 —— `begin()` 关掉 `SQL_ATTR_AUTOCOMMIT`，
  `commit()`/`rollback()` 走 `SQLEndTran` 之后**再打开**。这样「不在事务里的单条写入」仍然立即落库，
  不会因为忘记提交而静默丢数据（这是比「全局关 autocommit」更安全的默认）。
- `lastInsertId` 恒 0：各家取自增的方式不同（`@@IDENTITY` / `SCOPE_IDENTITY()` / Access 的 `@@IDENTITY`），
  由方言层按需生成 SQL；ODBC 没有统一入口。

### 三、本仓接线

- `session.Driver` 新增 `.odbc`（第 11 个驱动）；7 个方言共用它，方言差异仍由 `dialect.zig` 按 `Provider` 决定。
- `Dal.initWithModel` / `openDriverSession` / `supportsPooling` / `deinit` 全部接上；
  **`initWithModel` 与 `openDriverSession` 的 `switch` 至此已经没有 `else` 分支** ——
  编译器会强制「以后新增方言必须同时给执行路径」，这正是我们要的护栏。
- 连接串三种写法：① `Database=` 给完整 ODBC 串（含 `=` 和 `;`，原样用）；
  ② Access 给 `.mdb`/`.accdb` 路径 → `DRIVER={Microsoft Access Driver (*.mdb, *.accdb)};DBQ=...`；

### 三、接用例直接挖出一个真缺口：排序串解析

C# 的 `SqlBuilder.BuildOrder(PageParameter, factory)` 做三件事，本仓**一件都没有**：
1. `Sort` 串按 `,` 分段、清掉换行/制表；
2. 每段可带 `asc`/`desc` 后缀，没写后缀时用页面级 `Desc`；`asc` 段不写后缀、`desc` 段写 ` Desc`；

   「实体类[User]不包含排序字段[name2]」。

第 3 点是安全边界：后台列表页的 `?sort=xxx` 是外部输入，**直接把串拼进 ORDER BY 就是注入面**。
所以补了 `sqlbuild.buildOrderAlloc(gpa, table, spec, default_desc, mode)`：
- `mode = .sort`：上面的结构化口径；
- `mode = .order_by`：原样返回（C# 也如此：`OrderBy` 优先且 `Desc` 不生效）；
- 未知字段 → `error.UnknownSortField` + 打印「表 X 不包含字段 Y（该串来自外部输入，已拒绝）」。
